# PRD — 캘린더 반복·예정 수업 등록

> 상태: 확정안(구현 착수 전 최종 스펙). 작성: PM. 데이터 근거: 문의 2회("수업 추가 반복") + 헤비유저 미래날짜 선등록 20건(1명).
> 관련: `app_spec.md`(캘린더/기록), `design.md`(예정/완료 시각 규칙 — pd 갱신 예정), `lib/database.types.ts`(스키마 — pe 갱신 예정).
> ⚠️ 소표본(활성 약 10명) 기반 **가설 베팅**. 검증 목적의 좁은 MVP.

---

## 1. 문제 정의 & 목표

- **누구**: 정기적으로(주 N회 같은 요일·시간·장소·선생님) 수업받는 코어 유저.
- **마찰**: 반복 수업도 매회 처음부터 풀입력(record_date·start_time·end_time·mood·content 전부 필수). "예정"을 미리 잡아둘 수단이 없어 헤비유저가 미래 날짜 기록으로 우회.
- **목표**: (a) 반복 입력 부담 제거, (b) "예정" 선등록 → 수업 후 회고(mood·후기) 채우는 자연 흐름.
- **성공 판단**: 반복/예정 사용률, 예정→완료 전환율, 반복 유래 기록 비중, 문의 재발 감소.

---

## 2. 스코프

### MVP(1차)
- 기록에 **예정(planned) / 완료(done) 상태** 도입.
- 반복 등록: **매주 특정 요일(들) + 시간 + 템플릿(장소·선생님·레벨 등)** → 종료일까지 예정 다건 선생성.
- 예정은 **mood·content 없이** 생성/저장 가능.
- **예정→완료 전환 = mood 입력 시 자동 완료**(mood 미입력 저장은 예정 유지).
- 완료는 **단방향(monotonic)** — 한 번 done이면 mood를 지워도 예정으로 되돌아가지 않음. DB 트리거로 강제.
- 반복 회차 **단건 수정/삭제** + **"남은 예정 전체 삭제"**(status=planned 기준).
- 미래 단건 예정 등록(반복 없이).

### 후속(2차 이후) — 명시적 제외
- 복잡한 반복 규칙(격주·매월 n번째·요일별 다른 시간). MVP는 "매주 같은 요일·시간"만.
- this/following/all 분기 수정. MVP는 단건 예외 + 남은 전체 삭제만.
- **반복 규칙 자체 수정(요일·종료일 변경)**: MVP 제외(record_recurrences에 Update 경로 없음). **워크어라운드(G1)**: 규칙을 바꾸려면 "남은 예정 전체 삭제(§11.8) → 새 규칙으로 재등록(§11.2)". Create+Delete 조합으로 커버되며, 인라인 규칙 편집 UI는 후속.
- 예정 미완료 리마인더/푸시. **붙일 때 RN과 푸시 계약(딥링크·페이로드) 선협의 필수**(웹 단독 확정 금지).
- rolling 무한 반복(3개월 하드캡으로 대체).
- **기록 스트릭 시각화**: 후속. 단 예정/완료 상태가 스트릭 "완료 기준"의 선행 인프라가 됨.

| ID | 결정 | 값 |
|---|---|---|

| D2 | 헬스 연동 | 완료 전환 시점만 동기화(예정 배제) |

| D4 | 반복 종료조건 | 종료일 필수 + **3개월/약 26회 하드캡** |
| D5 | 예정 생성 시점 | 오늘 이후만(과거 소급 예정 불가) |
| D6 | 지난 예정 | 상태만 유지(자동 만료·리마인더 없음) |
| — | 완료 전환 | mood 입력 시 **자동 완료** |
| — | 완료 생명주기 | **단방향 monotonic**(done→planned 불가, 트리거 강제) |
| — | 반복 시작 | **오늘부터 즉시**(오늘 요일 매칭 시 오늘 포함) |
| — | "남은 삭제" 정의 | 해당 그룹의 **status=planned**인 회차(= 사실상 오늘 이후 미완료). done·과거 완료는 불변 |
| — | content | **optional**(예정·완료 모두 NULL 허용). 완료 트리거는 mood 단독 |

### 결정 간 정합성 노트(3차 적대 검수 반영)
- 완료를 mood **값**과 분리(단방향 latch)해 상태 왕복·D5 위반 차단.
- mood 없이도 완료 가능한 명시적 완료 경로 제공 → "출석·무mood" 통계 소실 방지.
- content optional화로 "mood만으로 완료" 트리거를 참으로 성립.
- 예정 편집은 status 유지(시간·장소 수정이 자동완료로 변질 안 됨).
- "남은"은 planned 기준 → D6(과거 예정 유지)과 충돌 없음.

## 4. 데이터 모델 (개념 — 스키마 확정은 pe)

### records (변경)
- `status`: `'planned' | 'done'` (기존 행은 전부 `'done'`으로 백필 — 하위호환). INSERT 컬럼 기본값 `NOT NULL DEFAULT 'done'`(§11.6).
- `mood`, `content`: **NULL 허용으로 완화**(예정은 비어 있음). done의 mood는 자동완료 트리거 값.
- `recurrence_id`: FK → record_recurrences (nullable; 단건 기록은 NULL).
- **반복 회차 취소 = 기존 `deleted_at` 재사용**(별도 취소 컬럼 없음). "취소된 예정"과 "삭제된 완료 기록"은 소프트 삭제 시점의 `status` 값으로 구분(`deleted_at IS NOT NULL AND status='planned'` = 취소된 예정 / `... AND status='done'` = 삭제된 완료). status가 단방향이라 사후 구분이 항상 안정적(§11.8).

### record_recurrences (신설)
반복 규칙 원본 1행 = 한 반복 그룹.
- `id`, `user_id`, `weekdays`(요일 집합), `start_time`/`end_time`, 템플릿(location·instructor·level 등), `starts_on`, `ends_on`, `client_request_id`(user_id와 복합 unique — 멱등키, §11.4), `created_at`, `deleted_at`.
- 그룹 자체 취소는 자식 planned 회차의 소프트 삭제로 충분(그룹 취소 컬럼 불필요, 필요 시 향후 추가).
- **고아 규칙 행 정책(G3, 의도적 결정)**: "남은 예정 전체 삭제"(§11.8) 후 자식이 전부 done/삭제돼도 **부모 규칙 행은 유지한다** — 별도 GC/삭제 없음. 어떤 조회도 규칙 행을 나열하지 않고(§7 지표는 records 기준), FK·통계에 무해하므로 방치가 정상. 원자 생성(§11.2·§11.7)으로 "자식 0인 규칙 행이 처음부터 생기는" 경로는 차단되며, 여기서 "유지"란 정상적으로 자식을 다 소진한 뒤 남는 규칙 행만을 뜻한다.

### 상태·생명주기 불변식
1. **monotonic**: `status`는 planned→done만. done→planned UPDATE는 **DB 트리거로 거부**.
2. 예정 생성 시 `record_date >= 오늘`(D5).
3. planned는 mood·content NULL 가능. done은 최소 mood 존재(자동완료 트리거 경로) 또는 명시적 완료.

## 11. pe 구현 정책 (§6 매트릭스 구멍 확정 — 착수 전 설계, 코드/마이그레이션 미작성)

> 작성: pe. 실제 코드·마이그레이션은 아직 적용하지 않음(⚠️ 이 라운드는 접근 정의만). 근거는 현재 코드베이스 실측(파일:라인) + Supabase 실 스키마 조회. 표기된 SQL/의사코드는 구현 방향을 보이기 위한 개념 스케치이며 최종 DDL이 아님.

### 11.1 (#14) 지난 예정 → 과거 날짜 완료 전환 시 헬스 조회 범위·정책

- **구현 접근**: 웹 쪽에는 "과거 조회"를 위한 별도 분기가 필요 없다. `requestHealthSyncFromApp({ requestId, date, activity })`(`lib/reactNativeWebView.ts:166-189`)는 임의의 `date` 문자열을 RN 앱에 전달만 하고, 실제 HealthKit/Health Connect 쿼리 범위는 네이티브 앱(별도 저장소, 이 repo 밖)이 결정한다. 웹 쪽 트리거인 `handleRequestHealthSync`(`app/record/new/page.tsx:712-731`, 동일 패턴 `app/record/[id]/edit/page.tsx:799` 부근)는 `!form.record_date` 진위값만 검사하고 오늘 대비 과거/미래 여부를 전혀 따지지 않는다(`app/record/new/page.tsx:713`). 즉 "완료 전환" UX를 **기존 기록 편집 폼 재사용**(예정 카드를 열어 mood를 채우면 자동완료, PRD 13행의 "회고 채우는 자연 흐름")으로 구현하면, 과거 날짜 예정이라도 기존 헬스 동기화 블록이 그대로 동작한다. 신규 코드 불필요, 정책은 "네이티브에 위임 + 기존 폼 재사용"으로 확정.
- **확실히 깨지는 지점**:
  1. PRD §6.2 표는 근거로 "M2"를 인용하지만 M2는 `app/api/admin/members` 어드민 집계 제외 항목(§5)이고, 헬스 연동 시점 결정은 **D2**다(§3). 문서 내부 인용 오류 — pm에 보고, 본 절 상단 매트릭스는 D2로 정정해 반영함.
  2. 헬스 동기화 토글은 `isIosHealthkit`(iOS+HealthKit only, `app/record/new/page.tsx:649-651`, `app/record/[id]/edit/page.tsx:727-729`)일 때만 노출된다. Android(Health Connect)는 타입만 정의(`HealthProvider`, `lib/reactNativeWebView.ts:74`)돼 있고 실제 동기화 버튼 게이팅에서 항상 제외된다. 이는 기존(반복/예정과 무관한) 제약이라 이번 스코프에서 새로 만들지 않지만, "지난 예정 완료 시 헬스 동기화" 기대 동작이 Android 유저에게는 애초에 노출되지 않는다는 점은 명시적으로 남겨야 함(회귀 아님, 기존 갭의 연장).
  3. 아주 오래된 지난 예정(D6: 자동 만료 없음 → 수개월 전 예정도 남아있음)을 오늘 완료 처리하면 네이티브 헬스 API가 기기 보관 기간 초과로 `NO_DATA`를 반환할 가능성이 큼 — 이미 `HealthSyncErrorCode`에 `NO_DATA`가 정의돼 있어(`lib/reactNativeWebView.ts:83-87`) 에러 처리 자체는 기존 경로로 충분히 커버됨. 다만 "너무 오래된 예정엔 동기화 버튼을 아예 숨길지"는 UX 판단이라 **pd 미해결**로 남김.

### 11.2 (#19, pm 확정 반영) 반복 생성 dedup을 RPC 트랜잭션 안에서 원자적으로 처리

- **구현 접근**: check-then-insert(먼저 SELECT로 겹치는지 확인 후 INSERT)는 동시 요청 사이에서 TOCTOU 레이스가 생겨 dedup을 보장하지 못한다. 대신:
  1. `records(user_id, record_date, start_time)`에 대해 **`WHERE deleted_at IS NULL` 조건의 partial unique index**를 추가한다(취소 표식이 `deleted_at` 재사용으로 통일됐으므로 조건 단일 — §11.8). 현재 `records`의 인덱스는 `records_pkey`, `records_user_id_idx`, `records_user_date_idx(user_id, record_date)`, `records_deleted_at_idx`뿐이고 `start_time`까지 포함한 유니크 제약은 없음(Supabase 실측: `pg_indexes`/`pg_constraint` on `public.records`, CHECK 제약은 `records_mood_range`/`records_time_order`/`records_workout_*`만 존재).
  2. 반복 생성 RPC(SQL/PL 함수, `SECURITY DEFINER`)는 **부모 `record_recurrences` INSERT와 자식 `records` 일괄 INSERT를 하나의 RPC 트랜잭션 안에서 순서대로 수행한다(G4, 부분 커밋 없음)** — 함수 호출 1건 = 트랜잭션 1건이므로, 부모만 커밋되고 자식이 안 들어가거나 그 반대인 상태가 **구조적으로 불가능**하다(예외 시 부모·자식 전부 롤백). 자식은 요일×종료일×26회 하드캡으로 산출한 후보 날짜 집합을 **하나의 `INSERT ... SELECT ... ON CONFLICT (user_id, record_date, start_time) WHERE deleted_at IS NULL DO NOTHING RETURNING record_date`** 문으로, 방금 만든 부모의 `recurrence_id`를 채워 삽입한다. 단일 SQL 문의 원자성(statement-level atomicity)이 dedup과 트랜잭션 원자성(§11.7)을 동시에 보장 — 동시 호출 두 건이 같은 슬롯을 놓고 경쟁해도 DB 레벨에서 하나만 성공한다(레이스에 강함, check-then-insert보다 우월).
  3. 응답은 `{ created: string[], skipped: string[] }`(요청 후보 날짜 - RETURNING 날짜 = skipped)로 반환해 프런트가 "겹치는 N일은 건너뛰었어요" 안내 + §11.3의 캐시 무효화에 그대로 사용.
- **해소된 리스크(취소 표식 통일)**: 초안에서는 반복 회차 취소를 별도 컬럼으로 두면 partial unique index에 취소·삭제 두 조건을 함께 걸어야 해(`deleted_at IS NULL AND <취소> IS NULL`) 취소된 슬롯 재생성이 막히는 오탐 리스크가 있었다. 취소 표식을 **`deleted_at` 재사용으로 확정(§4, §11.8)**하면서 조건이 `WHERE deleted_at IS NULL` 하나로 단순해져 이 분기·오탐 리스크가 **원천 제거**됐다. 취소된 예정(`deleted_at IS NOT NULL AND status='planned'`)은 소프트삭제 상태라 유니크 슬롯을 점유하지 않으므로 재생성이 정상 허용된다.

### 11.3 (#39) 반복 생성/삭제의 dirty flag 무효화 범위 — 정확히 어느 날짜들인가

캐시가 세 종류로 나뉘고, 날짜 단위 정밀도가 필요한 건 그중 하나뿐이다.

- **`lib/calendarHomeCache.ts:14-15`**: `monthDataDirty`는 **전역 boolean**(월별 Map이지만 dirty 플래그는 날짜 무관 단일 값), `invalidateCalendarCache()`(`lib/calendarHomeCache.ts:30-32`) 호출 1회로 전체 무효화됨. 반복 생성이 몇 개 날짜에 걸치든 **1회 호출로 충분**.
- **`lib/profileCache.ts`/`lib/profileRecordsCache.ts`**: 둘 다 `userId` 단위 dirty set/flag(`profileDirtySet`, `entry.dirty`)이지 날짜 단위가 아님. `invalidateProfileCache(user.id)`/`invalidateProfileRecordsCache(user.id)` **1회 호출로 충분**(기존 단건 기록 생성/수정 플로우에서도 이미 1회만 호출 — `app/record/new/page.tsx:954-955`, `app/record/[id]/edit/page.tsx:987-988`).
- **`sessionStorage["record-changed:{date}"]` — 여기가 진짜 날짜 단위 정밀도가 필요한 지점**:
  - `app/(tabs)/calendar/page.tsx:251-256`(및 `:281-286`)는 접두사 `record-changed:`로 시작하는 키가 **하나라도 있으면** 무조건 전체 갱신 — 정확한 날짜값은 검사하지 않음.
  - 반면 `app/day/[date]/page.tsx:117-130`은 `record-changed:${dateStr}`로 **정확히 그 날짜 키**만 검사한다. 즉 반복 생성으로 A, B, C 세 날짜에 예정이 생겼는데 `record-changed:A`만 세팅하면, 유저가 캘린더에서 B나 C 날짜의 day뷰로 들어갔을 때 새로 생긴 예정 카드가 안 보인다(하드 새로고침 전까지 stale) — day뷰는 날짜별로 독립적으로 캐시되기 때문.
  - **정책**: RPC 응답의 `created`(§11.2) / 취소된 날짜 목록(§11.8, "남은 전체 삭제" 응답)에 있는 **모든 날짜 각각**에 대해 `sessionStorage.setItem(`record-changed:${d}`, "1")`을 반복 호출한다. 단건 흐름(`app/record/new/page.tsx:957`)의 "현재 폼의 record_date 하나만 세팅" 패턴을 다중 날짜 케이스에 그대로 복붙하면 위 버그가 그대로 재현되므로, 구현 시 명시적으로 배열 순회로 바꿔야 함 — **가장 흔한 실수 지점으로 표시**.
  - skip된(dedup으로 건너뛴) 날짜는 실제로 아무것도 쓰지 않았으므로 day뷰를 갱신할 필요가 없다 — `created`/취소 목록에만 한정하면 됨(과잉 무효화 방지, 26개 키 setItem 자체는 성능 이슈 아님).

### 11.4 (#40) 반복 생성 더블탭 멱등성 — 서버/클라 역할 분담

3중 방어로 설계(각 레이어가 서로 다른 실패 모드를 막음, 하나만으론 부족):

1. **클라 — 동기 ref 가드**: 기존 패턴(`app/record/new/page.tsx:1653` `disabled={saving}`)은 React state 기반이라 재렌더 커밋 전 한 프레임(~16ms) 안에 들어오는 두 번째 탭 이벤트는 여전히 핸들러를 통과할 수 있다(state 업데이트는 비동기, 두 탭이 같은 이벤트 루프 틱 안에서 들어오면 둘 다 `disabled` 반영 전에 실행됨). 반복 생성은 실패 결과(중복 그룹)가 단건보다 무거우므로, 버튼 onClick 최초 진입점에서 `useRef<boolean>` 동기 플래그로 즉시 재진입을 차단하는 걸 추가 요구사항으로 둔다(state와 별개로 ref는 같은 틱에서도 즉시 최신값 확인 가능).
2. **클라 — idempotency key**: 기존 `createRequestId()`(`app/record/new/page.tsx:168-173`, 헬스싱크 상관관계 ID로 이미 쓰이는 유틸) 패턴을 재사용해 생성 요청마다 클라이언트가 UUID를 만들어 RPC에 `p_client_request_id`로 전달. `record_recurrences`에 `client_request_id`(user_id와 복합 unique) 컬럼을 두면, 네트워크 재시도(첫 응답이 타임아웃돼 클라가 실패로 오인하고 같은 요청을 다시 보내는 경우)에서도 같은 키로는 새 그룹을 만들지 않고 기존 그룹 결과를 그대로 반환한다.
3. **서버 — §11.2의 partial unique index가 최종 방어선**: 1·2가 뚫려도(예: 사용자가 두 개의 다른 탭에서 각각 새 요청ID로 "따로" 두 번 실제 제출) `records`에 대한 slot 유니크 인덱스가 실제 회차 row 중복 생성만은 막는다. 이 경우 두 번째 호출의 자식 INSERT는 전부 `ON CONFLICT`로 스킵(created=0)된다. **주의(§11.7과의 정합)**: `ON CONFLICT DO NOTHING`으로 0건이 된 것은 예외가 아니라 "정상 스킵"이라 자동 롤백되지 않는다 → 방치하면 부모 규칙 행만 자식 0으로 커밋되는 고아가 생긴다. 따라서 **RPC는 "created 개수 = 0이면 명시적으로 트랜잭션 중단(RAISE)"하거나, 부모 INSERT를 자식 ≥1건 확정 이후로 배치**해야 한다(G4 요구사항). 이 명시적 가드가 있어야만 "부모+자식 원자성"이 완성되고 최종 상태가 "중복 회차 없음 + 고아 부모 없음"으로 정합해진다(종전 초안의 "자식 0 고아 부모가 남는다"는 이 가드로 폐기). §7 지표(records 기준)도 왜곡 없음.
- **확실히 깨지는 지점**: 1번만 하고 2·3번을 생략하면(가장 흔한 축소 구현), "새로고침 직후 재탭"이나 "느린 네트워크에서 첫 요청이 아직 안 끝났는데 앱을 백그라운드→포그라운드 전환 후 재탭" 같은, 같은 틱이 아닌 정상적인 재요청 시나리오에서 중복 그룹이 그대로 생성된다. ref 가드는 "빠른 더블탭"만 막고 "느린 네트워크 재시도"는 못 막으므로 반드시 서버측(idempotency key 또는 최소한 §11.2 인덱스)이 같이 있어야 함.

### 11.5 (#41) 예정→완료 PATCH 동시성과 M5 트리거의 관계

- **레이스가 실제로 생기는 지점**: `app/api/records/[id]/route.ts:136-140`의 PATCH는 폼 전체 스냅샷을 `.update(normalizedPayload)`로 통째로 덮어쓴다(부분 patch가 아님, diff 기반이 아님). 두 기기/탭이 같은 예정 레코드를 동시에 열어 하나는 mood를 채워 완료 전환을 시도하고 다른 하나는 mood 없이 장소만 고쳐 저장하면, **나중에 도착하는 요청의 스냅샷이 이긴다** — 완료 전환이 나중이면 정상 완료되지만, "장소만 수정"(mood=null 포함한 stale 스냅샷)이 나중에 도착하면 이미 done인 행에 mood=null을 덮어씌우려는 시도가 된다.
- **M5와의 관계**: PRD 25행 "완료는... mood를 지워도 예정으로 되돌아가지 않음"이 이미 이 케이스의 결과를 규정한다 — M5 트리거는 `status` 컬럼의 done→planned 역행만 거부하고, done 행의 mood가 null로 바뀌는 것 자체는 허용(트리거가 막을 필요 없음, 이미 PRD가 명시적으로 허용). 즉 이 특정 파괴적 결과는 **M5의 스코프 밖이며 이미 PRD가 "허용"으로 답한 케이스**라 새로운 트리거 로직 불필요.
- **앱단에서 채워야 할 것(이번에 확정)**: "레이스 자체를 줄이는" 낙관적 동시성 체크. `records`에는 이미 `updated_at`(NOT NULL, `now()` 기본값) 컬럼과 `records_set_updated_at` BEFORE UPDATE 트리거(Supabase 실측: `pg_trigger` on `public.records`)가 있어 매 UPDATE마다 자동 갱신된다. 폼 로드 시점의 `updated_at`을 hidden state로 들고 있다가 PATCH 바디에 `expected_updated_at`으로 실어 보내고, 서버는 UPDATE 전에 현재 행의 `updated_at`과 비교해 불일치하면 `409 Conflict`로 거절 → 클라는 "다른 기기에서 방금 이 기록이 바뀌었어요, 새로고침해 주세요" 토스트. 새 컬럼/마이그레이션 불필요, 기존 컬럼·트리거 재사용.
- **확실히 깨지는 지점**: #12(이미 done을 재완료 — 멱등, 변화 없음)와 혼동하지 말 것. `updated_at` 비교를 "값이 다르면 무조건 409"로 구현하면, 같은 유저가 같은 폼을 두 번 연속 제출(더블탭, mood 값 동일)하는 정상적인 멱등 케이스까지 막힐 수 있다 — 409는 "다른 세션에서 실제 필드값이 달라진 경우"에만 발동하도록, 비교 대상은 `updated_at`이지만 판정은 "필드값이 실질적으로 달라졌는지"까지 서버가 한 번 더 확인하거나, 최소한 에러 메시지에서 #12와 #41을 구분해 사용자에게 혼란을 주지 않아야 함.

### 11.6 (#43) 구버전 클라이언트 status 미전송 시 default 정책

- **구현 접근**: `records.status`에 `NOT NULL DEFAULT 'done'` 컬럼 기본값을 건다(백필 기준선인 "기존 행 전부 done"과 동일한 값이라 정합적). 구버전 앱은 POST 바디에 `status` 키 자체를 안 보내므로 INSERT 시 컬럼이 생략되고 DB 기본값 `'done'`이 그대로 적용 — 서버 라우트에 "미전송이면 done으로 간주" 같은 분기를 추가할 필요가 없다.
- **왜 이게 정합적인가**: 현재 `app/api/records/route.ts:80-99`, `app/api/records/[id]/route.ts:106-125`는 이미 `mood`를 1~8 범위의 **필수값**으로 검증하고 있다 — 구버전 클라는 애초에 mood 없이 저장할 방법이 없다. PRD의 완료 규칙("mood 입력 시 자동 완료")과 결합하면, 구버전 클라의 모든 쓰기는 "mood 필수 + status 미전송" = "완료 조건을 항상 만족하는 쓰기"이므로 default 'done'이 실제 동작과 100% 일치한다. 신버전 클라만 `status: 'planned'`를 명시적으로 보내 mood/content 필수 검증(M6)을 우회하는 새 경로를 타면 된다.
- **확실히 깨지는 지점**: M6에서 "예정 편집은 status 유지"라 했는데, 만약 구현이 "PATCH 바디에 status가 없으면 무조건 default('done')로 되돌린다"는 식으로 default 정책을 INSERT뿐 아니라 PATCH 페이로드 구성에도 잘못 적용하면, **구버전 클라가 planned 레코드를 다른 필드만 고쳐 PATCH할 때 의도치 않게 강제 완료**되어 버린다(신버전이 만든 planned 레코드를 구버전 클라가 열어서 저장하는 크로스 버전 시나리오 — 앱스토어 배포 특성상 신·구버전 공존 기간에 실제로 발생 가능). 정책은 "**INSERT의 컬럼 기본값**"으로만 걸고, PATCH 경로는 §5 M6대로 "기존 행의 현재 status를 유지, 클라가 보낸 값으로 명시적으로 덮어쓰지 않는다"로 명확히 분리해야 함 — default 정책이 INSERT/PATCH 두 경로에 다르게 적용된다는 점이 이번 라운드에서 명시적으로 확정해야 했던 부분.

### 11.7 (#44) 반복 생성 부분 실패 원자성 — RPC 트랜잭션 범위

- **구현 접근**: RPC를 **단일 SQL/PL 함수**로 만들고, 그 안의 핵심 쓰기를 §11.2에서 정의한 **단일 `INSERT ... SELECT ... ON CONFLICT DO NOTHING`** 한 문장으로 구성한다. Postgres에서 함수 호출 1건 = 암묵적 트랜잭션 1건이고, 다중 행 INSERT 한 문장도 statement-level에서 원자적이다(이 SELECT/generate_series 기반 후보 생성부터 INSERT까지 루프 없이 set-based로 처리하면 "일부만 커밋"이 애초에 발생할 수 없는 구조).
- **"부분 실패"와 "정상 스킵"을 구분하는 게 핵심**: dedup으로 인한 skip(§11.2)은 `ON CONFLICT DO NOTHING`이 처리하는 **정상 동작**이지 실패가 아니다 — 응답의 `skipped` 배열로 표현. 진짜 실패(제약 위반, DB 커넥션 에러 등)는 INSERT 문 자체가 예외를 던지고, 그 순간 함수 전체가 롤백되어 **0건도 생성되지 않는다**(전부 롤백, 부분 커밋 없음). 즉 정책은 "생성은 전부-아니면-전무(all-or-nothing), 예외는 26건 중 몇 건이 아니라 호출 전체 단위로만 발생"으로 확정 — "부분 커밋 + 재시도" 옵션은 애초에 구조상 선택지가 아니게 설계.
- **created=0(전부 스킵) 시 부모 고아 방지(G4 연결)**: 위처럼 전부 스킵은 예외가 아니라 정상 커밋이므로, **신규 그룹인데 자식이 0건이면 부모 규칙 행만 남는 고아**가 된다. 이를 막기 위해 RPC는 "created=0이면 명시적으로 `RAISE`해 트랜잭션 중단" 또는 "부모 INSERT를 자식 ≥1건 확정 후 배치"를 **반드시 포함**한다(§11.4 3번과 동일 규칙). 단, 멱등키(§11.4 2번)로 기존 그룹을 재조회해 반환하는 경로는 예외 — 이 경우는 "이미 만든 것을 그대로 돌려주기"라 새 부모를 안 만들므로 고아가 아니다.
- **확실히 깨지는 지점**: 만약 구현을 set-based INSERT 대신 "날짜별 for-loop + 개별 INSERT + 실패 시 continue" 방식의 PL/pgSQL로 짜면(직관적으로 짜기 쉬운 형태), 정확히 PRD가 우려하는 "26건 중 일부만 커밋" 상황이 실제로 만들어진다 — 루프 내 개별 INSERT는 각각이 서브트랜잭션이 아니므로 하나가 실패하면 전체 함수가 예외로 죽거나(SAVEPOINT 없이), SAVEPOINT를 걸면 반대로 의도적 부분 커밋이 되어버린다. **이번 정책상 루프 기반 구현은 채택하지 않음**을 명시적으로 남겨야 함 — 이는 구현 착수 시 "쉬운 길"로 잘못 갈 수 있는 지점이라 특히 표시.

### 11.8 (#45) "남은 예정 전체 삭제" 원자성 + 취소 표식 정합(확정)

- **소유권 스코프(G5, 보안·필수)**: "남은 삭제"의 단일 UPDATE는 **반드시 `user_id`를 WHERE에 포함**해야 한다 — `UPDATE records SET deleted_at = now() WHERE recurrence_id = $1 AND user_id = <caller> AND status = 'planned' AND deleted_at IS NULL`. `recurrence_id`만으로 걸면 그 값을 아는(또는 추측한) 타인이 남의 예정을 삭제하는 IDOR가 된다. `<caller>`는 `getUserFromRequest`로 검증된 세션 유저. 동등한 대안: 실행 전 `record_recurrences`(또는 대표 record) 1행을 SELECT해 `user_id != caller`면 **403**, 없으면 **404**로 거른 뒤 UPDATE — CLAUDE.md "PATCH/DELETE 전 소유권 조회, 없으면 404·타인 소유면 403" 규칙 준수. WHERE에 user_id를 넣는 방식이 더 단순하며 원자성도 유지.
- **원자성**: API 라우트가 대상 레코드 id 목록을 받아 **개별 UPDATE를 반복 호출**하는 방식(클라가 목록을 순회하며 기존 단건 삭제 엔드포인트를 N번 호출)은 절대 쓰지 않는다 — 이 경우 중간에 네트워크가 끊기면 정확히 PRD가 우려하는 "일부만 취소됨" 상태가 남는다. 대신 위의 **소유권 스코프가 걸린 단일 UPDATE** 문 하나로 처리한다 — 다중 행에 걸친 단일 UPDATE 문도 statement-level에서 원자적이라(매칭되는 모든 행이 같은 트랜잭션 안에서 함께 성공하거나 함께 실패), "부분 실패"가 구조적으로 발생하지 않는다.
- **취소 표식 = `deleted_at` 재사용(확정)**: PRD가 pe에게 위임했던 "별도 취소 컬럼 vs `deleted_at` 재사용" 판단을 **`deleted_at` 재사용으로 확정**하고 §4 본문에 반영했다. 근거: 이 repo의 "예정 제외/미노출" 계열 쿼리는 예외 없이 전부 `.is("deleted_at", null)` 한 조건에만 의존한다(캘린더 `app/(tabs)/calendar/page.tsx:155,240`, day뷰 `app/day/[date]/page.tsx:107`, M3 대상 전체, SQL 함수 3개 모두 `deleted_at IS NULL`만 검사, §11.2 인덱스도 `records_deleted_at_idx` 하나뿐). 별도 취소 컬럼을 신설했다면 이 6곳+SQL 3개+어드민+공개프로필 **전부에 `AND <취소> IS NULL`을 빠짐없이 추가**해야 유령 카드가 안 남는데, 하나라도 누락하면 즉시 회귀. `deleted_at` 재사용은 이 전파 리스크를 **구조적으로 제거**한다.
- **취소/삭제 구분은 status로**: "취소된 예정"(`deleted_at IS NOT NULL AND status='planned'`)과 "삭제된 완료 기록"(`... AND status='done'`)은 소프트삭제 시점의 status 값으로 항상 구분 가능(status 단방향이라 안정적). 별도 컬럼 없이도 사후 분석·복원에 충분.
- **정합 완료**: 이 결정으로 §4 데이터 모델·§11.2 인덱스 조건·본 절이 모두 `deleted_at` 단일 조건으로 일치. 잔여 상충 없음.

### 11.9 (#46) 네트워크 실패 시 낙관적 업데이트 롤백 정책

- **선행 사실 확인**: 이 repo의 기록 생성/수정(`app/record/new/page.tsx`, `app/record/[id]/edit/page.tsx`)은 현재 **낙관적 업데이트를 전혀 쓰지 않는다** — 제출 버튼은 `disabled={saving}`(`app/record/new/page.tsx:1653`)으로 잠기고, 서버 응답을 `await`한 뒤에야 화면이 바뀐다(성공 시 이동, 실패 시 toast). 캘린더/day뷰도 마운트·`pageshow`·`popstate` 시점에 서버에서 다시 fetch하는 구조(§11.3)일 뿐, 로컬 state를 미리 낙관적으로 바꿔놓고 실패 시 되돌리는 코드 경로가 어디에도 없다.
- **구현 접근**: 반복 생성/완료 전환/남은 전체 삭제도 **같은 아키텍처를 유지**한다 — 낙관적 UI를 새로 도입하지 않고, 요청 중 버튼 비활성화 + 스피너, 실패 시 toast만 띄우고 로컬 state는 애초에 건드리지 않았으므로 "롤백"이라는 별도 로직 자체가 필요 없다(적용한 적 없는 변경은 되돌릴 것도 없음). 성공 시에만 §11.3의 캐시 무효화 + refetch로 화면을 갱신한다. 이 방식은 기존 코드 패턴과 100% 일관되고, 낙관적 업데이트 구현에 따르는 새로운 버그 표면(부분 롤백, race with refetch 등)을 아예 만들지 않는다.
- **정합 확인(pd↔pe)**: 로딩 표현은 §9.12에서 **기존 LoadingOverlay 재사용(낙관적 업데이트 없음)**으로 확정됐고, 위 pe 아키텍처("낙관적 UI 미도입")와 일치한다. `docs/design.md`는 아직 이 PRD 관련 시각 규칙(예정/완료 카드·로딩)을 반영하지 않았으므로, **pd가 design.md를 갱신할 때 §9.12 전제(로딩=LoadingOverlay, 낙관적 표시 없음)를 그대로 명문화**하면 된다 — pe 결정과 충돌 없음. 로딩 인디케이터의 정확한 스타일은 §9.12(LoadingOverlay)로 귀결.

## 12. 신규 엔드포인트 공통 규칙 & Read 견고성 (CRUD 감사 반영)

- **§12.1 소유권·소프트삭제 일관(G5 일반화)**: 이번에 신설되는 **반복 생성 RPC/엔드포인트**와 **"남은 예정 전체 삭제" 엔드포인트**는 기존 `PATCH /api/records/[id]`·`DELETE /api/records/[id]/delete`와 **동일한 인증·소유권 패턴**을 따른다 — `getUserFromRequest`로 세션 유저 확정, 대상 부재 시 **404**, 타인 소유 시 **403**(CLAUDE.md 규칙). 반복 생성 시 자식 `records`·부모 `record_recurrences` 모두 `user_id`를 세션 유저로 세팅하고, dedup 유니크(§11.2)·"남은 삭제" UPDATE(§11.8) 조건에 `user_id`를 포함해 **타 유저 데이터에 절대 교차 접근 불가**. 삭제는 전부 **소프트삭제(`deleted_at`)** 로 통일(하드 삭제 없음), 조회·필터는 `deleted_at IS NULL` 일관 적용.
- **§12.2 planned Read null-safe(G7)**: 예정 기록은 `mood`가 **null**, `content`는 **빈 문자열("")** 이다(현행 API가 content를 ""로 정규화 — DB `content`는 NOT NULL). 상세/카드 Read(`record/[id]/page.tsx`, 캘린더·day 카드 등)는 mood 아이콘·후기 텍스트가 없어도 **크래시 없이 렌더**해야 한다(빈 상태 처리). 기존 렌더가 "mood 항상 존재/content 비어있지 않음" 가정을 깔고 있으면 예정에서 깨지므로, pe는 구현 시 이 지점을 **null/empty-safe로 점검**(§9.4 완료 유도 UI·§9.11 미디어 숨김과 연결). select에 `status`·`recurrence_id`를 포함(M3)해 렌더 분기의 근거로 사용.

- **§12.3 완료 전환 시 헬스 동기화 오류 처리(RN 요청 반영, Phase 4)**: 완료 전환은 호출 시점이 기존 작성 화면보다 넓어져 `health_sync_request` 겹침 빈도가 올라간다. RN과 확정한 두 케이스:
  1. **진행 중 겹침 → `QUERY_FAILED("already in progress")`**: 웹은 이 코드를 **재시도하거나 조용히 무시**한다 — **사용자에게 에러 토스트를 띄우지 않는다**(정상적 경합이지 사용자 오류가 아님). 완료 자체(mood 저장/status 전이)는 헬스 결과와 **독립적으로 성공** 처리하고, 헬스 값은 다음 성공 응답 때 채운다.
  2. **Android(헬스 미지원) → `NO_PERMISSION`**: 완료 전환 플로우도 **기존 작성 화면과 동일한 에러 핸들러 `getHealthSyncErrorMessage`를 재사용**해 처리(신규 분기 금지). Android는 애초에 헬스 토글이 노출되지 않는 기존 제약(§11.1) 위에서 동작하므로, 이 경로는 방어적 일관성 차원.
  - 두 케이스 모두 **헬스 실패가 완료 전환을 막지 않는다**(헬스는 부가 데이터). 리마인더 푸시는 후속이며 붙일 때 RN 계약 선협의(§2 후속).
