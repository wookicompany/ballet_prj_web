## 1. 개요

| 항목 | 내용 |
|---|---|
| 목표 | 본 공연을 캘린더에 포스터로 쌓아가는 **개인 관람 아카이브**를 만들고, 그 기록에서 리뷰가 자연스럽게 커뮤니티로 흘러가게 한다 |
| 배경(데이터) | 최근 30일 공연 조회 **64건(7.1배↑)** 인데 리뷰 2·댓글 0·예매 0 → **탐색 수요는 있으나 소셜 강제는 실패**. 반면 개인 기록(캘린더)은 리텐션 100% → **"개인 먼저, 커뮤니티는 결과"** 로 재포지셔닝 |
| 진입 | 공연 탭 상단 아이콘 (탭바 4개 유지) |
| 원칙 | KST 날짜, 소프트 삭제, 쓰기는 서버 API, 전체 실패(all-or-nothing), 어요체·가운뎃점 없음 |

## 2. 기능 리스트 (V1 확정)

| 대분류 | 중분류 | 소분류 | 내용 |
|---|---|---|---|
| **티켓북 홈** | 캘린더 | 포스터 표시 | 관람한 날짜 셀에 공연 **포스터 썸네일** 노출 |
| | 캘린더 | 날짜 탭 | 그날 본 공연 목록(포스터·공연명·장소·별점) |
| | 캘린더 | 기간 이동 | 년·월 앞뒤 이동 |
| | 썸네일 | 대체 규칙 | 포스터 없으면 첨부 이미지 1번째 → 둘 다 없으면 플레이스홀더 |
| **티켓 등록** | 진입 | + 버튼 | 티켓북 홈에서 "티켓 등록하기" |
| | 공연 선택 | KOPIS 검색 | 공연명 검색 → 선택 시 **포스터·공연명·장소 자동 입력** |
| | 공연 선택 | 직접 입력 | DB에 없는 공연은 공연명·장소 직접 입력 |
| | 입력 항목 | 관람 날짜 | **필수** |
| | 입력 항목 | 별점 | 선택 |
| | 입력 항목 | 좌석 | 선택 |
| | 입력 항목 | 이미지 | 선택, **최대 3장** |
| **이미지** | 첨부 | 장수 제한 | 최대 3장 |
| | 첨부 | 처리 방식 | 기존 기록 미디어와 동일한 **압축·스토리지 패턴 재사용** |
| | 첨부 | 썸네일 활용 | 직접 입력 공연은 **첫 이미지가 캘린더 썸네일** |
| **티켓 관리** | 상세 | 화면 구성 | 포스터 + 공연 정보 + 별점·좌석·메모 + 첨부 사진 |
| | 수정 | — | 등록 항목 전체 수정 |
| | 삭제 | — | **소프트 삭제**(deleted_at) |
| **커뮤니티 연계** | 리뷰 작성 | 진입 | 티켓 상세에서 "리뷰 쓰기" |
| | 리뷰 작성 | 내용 | **티켓의 별점 재사용** + 리뷰 본문 작성 |
| | 공개 설정 | 공개 / 비공개 | 기본 **비공개**, 공개 시 커뮤니티 노출 |
| | 노출 | 공연 상세 | 공개한 리뷰는 해당 **공연 상세의 리뷰 목록**에 표시 |
| | 제약 | 직접 입력 공연 | KOPIS 공연이 아닌 건은 **커뮤니티 노출 불가**(개인 기록만) |
| **진입점** | 위치 | 공연 탭 | 공연 탭 상단 아이콘 |

## 3. 화면 스펙

### S1. 진입점 — 공연 탭
| 구성 | 내용 |
|---|---|
| 위치 | 공연 탭 상단 우측 아이콘(티켓 모양) |
| 액션 | 탭 → 티켓북 홈(S2) |

### S2. 티켓북 홈 — 월 캘린더
| 구성 | 내용 |
|---|---|
| 캘린더 | 월 그리드. 관람일 셀에 **포스터 썸네일**(메인 기록 캘린더와 구분: 무드·점선 없음) |
| 하루 2건 이상 | 첫 포스터 + 우상단에 총 개수 배지 |
| 날짜 탭 | 하단에 그날 공연 목록(포스터·공연명·장소·별점) → 항목 탭 시 상세(S5) |
| 기간 이동 | 년·월 앞뒤 이동 |
| 추가 | 우하단 **+ 버튼** → 공연 선택(S3) |
| 빈 상태 | "본 공연을 티켓북에 담아보세요" 안내 + 등록 버튼 |

### S3. 티켓 등록 ① 공연 선택
| 구성 | 내용 |
|---|---|
| 검색 | 공연명 입력 → KOPIS 공연 목록(포스터·공연명·기간·장소) |
| 선택 | 공연 선택 시 정보 자동 채우고 S4로 |
| 직접 입력 | "찾는 공연이 없어요" → 공연명·장소 직접 입력 후 S4로 |

### S4. 티켓 등록 ② 정보 입력
| 구성 | 내용 |
|---|---|
| 상단 | 선택한 공연 요약(포스터·공연명·장소) |
| 관람 날짜 | **필수**, 기본 오늘(KST) |
| 별점 | 선택, 1~5 |
| 좌석 | 선택, 자유 텍스트 |
| 메모 | 선택, 자유 텍스트 |
| 이미지 | 선택, **최대 3장**(압축 후 업로드) |
| 저장 | 서버 API, 실패 시 전체 실패 + 토스트 |

### S5. 티켓 상세 · 수정 · 삭제
| 구성 | 내용 |
|---|---|
| 상세 | 포스터 + 공연 정보 + 관람일·별점·좌석·메모 + 첨부 사진 |
| 리뷰 | "리뷰 쓰기" 버튼 → S6 (직접 입력 공연은 **비활성 + 사유 안내**) |
| 수정 | 등록 항목 전체 수정 |
| 삭제 | 소프트 삭제, 확인 다이얼로그 |

### S6. 리뷰 작성 · 공개 설정
| 구성 | 내용 |
|---|---|
| 별점 | 티켓 별점 **자동 반영**(수정 가능) |
| 본문 | 리뷰 텍스트 |
| 공개 설정 | **기본 비공개** 토글. 공개 시 공연 상세 리뷰 목록에 노출 |
| 저장 | `performance_reviews`에 저장, 티켓과 연결 |

## 4. 데이터 모델

> **변경 이력**: 메모(`memo`)는 v1에서 제거했다(마이그레이션 `ticket_book_drop_memo`).
> 리뷰에 공개/비공개 토글이 있어 "나만 보는 감상"은 비공개 리뷰가 담당하므로, 자유 텍스트
> 입력란이 둘이면 더 위에 있고 부담 없는 메모에 쓰게 되어 리뷰가 비게 된다. 티켓북의 기획
> 의도(개인 기록에서 리뷰가 커뮤니티로 흘러가게 한다)와 정면으로 충돌한다.

### 신규 `performance_tickets`
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id / user_id | uuid | PK / 소유자 |
| performance_id | text, nullable | KOPIS 공연 참조. **null이면 직접 입력** |
| custom_title / custom_venue | text, nullable | 직접 입력용 공연명·장소 |
| watched_on | date | 관람 날짜(KST, 필수) |
| rating | smallint, nullable | **2~10 짝수**(기존 리뷰와 동일 스케일, 별 1개 탭 = 2점). `performance_reviews.rating`과 동일한 CHECK(`rating IS NULL OR (rating BETWEEN 0 AND 10 AND rating % 2 = 0)`) 적용 — 변환 로직 없이 그대로 리뷰에 복사해 연결한다 |
| seat | text, nullable | 좌석 |
| review_id | uuid, nullable | 연결된 리뷰(`performance_reviews.id`) |
| created_at / updated_at / deleted_at | timestamptz | 소프트 삭제 |

### 신규 `performance_ticket_images`
id, ticket_id, url, created_at, deleted_at (최대 3장, `record_media` 패턴 재사용)

### 기존 `performance_reviews` 변경
`is_public boolean NOT NULL DEFAULT true` 추가
- 기존 리뷰는 전부 공개 유지 → **회귀 없음**
- 커뮤니티 노출 쿼리(공연 상세 리뷰 목록 등)에 `is_public = true` 필터 추가 필요

## 6. 리스크 · 확인 필요

| 항목 | 내용 |
|---|---|
| **RLS 미변경 시 전면 유출(최상위 리스크)** | `performance_reviews`에 `is_public` 컬럼만 추가하고 `performance_reviews_select` RLS 정책(현재 `deleted_at IS NULL`만 조건 — 사실상 전체 공개)을 함께 교체하지 않으면, 화면 코드가 서버 API를 거치지 않고 `supabase.from("performance_reviews")`로 직접 조회하는 구조상(예: 공연 상세·리뷰 상세 페이지) **비공개 리뷰가 RLS 우회 없이도 그대로 읽힌다**. 컬럼 추가와 RLS 정책 교체는 반드시 한 마이그레이션에서 함께 배포한다 — §8 DB 마이그레이션 참고 |
| **`u/[id]` 공개 프로필 리뷰 수 유출(최상위 리스크)** | 공개 프로필 요약 API(`/api/public-profiles/[id]/summary`)는 service role로 RLS를 우회하므로, `review_count` 집계 쿼리에 `is_public = true` 필터를 명시적으로 추가하지 않으면 타인의 비공개 리뷰 개수가 SNS 공유용 공개 프로필에 그대로 노출된다 |
| 리뷰 공개 필터 누락(전수 점검) | `is_public` 추가 시 기존 리뷰 조회처를 전부 찾아 필터를 적용해야 함(공연 상세·검색·집계 뷰·어드민 등) — 파일:라인 단위 점검표는 §8 "is_public 노출처 전수 점검표" 참고 |
| ~~리뷰 중복~~ → **확정: 제약 불필요** | `performance_reviews`엔 원래 `(user_id, performance_id)` 유니크 제약이 없고, 기존 커뮤니티 리뷰 작성 플로우도 중복 생성을 막지 않는다. 즉 한 유저가 같은 공연에 리뷰를 여러 개 남기는 것은 오늘도 허용되는 동작 — 티켓 1개당 리뷰 최대 1개 구조와 자연스럽게 맞으므로 신규 중복 방지 로직을 추가하지 않는다 |
| ~~별점 스케일~~ → **확정** | `performance_tickets.rating`은 `performance_reviews.rating`과 동일한 스케일(2~10 짝수, 별 1개 탭 = 2점)로 저장한다. 리뷰 연결 시 변환 로직 없이 그대로 복사한다 |
| ~~티켓 삭제 시 리뷰 처리~~ → **확정** | 티켓을 소프트 삭제해도 연결된 리뷰는 삭제하지 않고 유지한다. 리뷰는 독립 엔티티로 계속 공연 상세 리뷰 목록에 노출되며, 티켓의 `review_id`도 그대로 남긴다 |
| ~~리뷰 공개 재전환~~ → **확정: v1 제외** | 공개/비공개는 **리뷰 작성 시점에만** 정한다. 기존 `PATCH /api/reviews/[id]`가 `rating`을 항상 재검증하는 구조라 부분 업데이트를 지원하려면 핸들러를 고쳐야 하고, 이는 기존 리뷰 수정 플로우의 회귀 위험을 동반한다. v2 선행 조건은 §8.5에 기록 |
| ~~티켓 사진 RLS~~ → **확정** | `performance_ticket_images` SELECT 정책은 `performance_review_images`(공개 리뷰용, `USING (true)`)가 아니라 **`record_media` 패턴(`user_id = (SELECT auth.uid())`)**을 따른다. `record-media` 버킷이 public이라 `true`로 두면 전체 유저의 티켓 사진이 유출된다 — §8 DB 마이그레이션 5번 |
| ~~리뷰 생성 멱등성~~ → **확정: 409 필수** | `POST /api/tickets/[id]/review`는 `ticket.review_id`가 이미 있으면 409를 반환한다. 없으면 더블탭·재시도로 티켓과 끊긴 리뷰가 커뮤니티에 노출된다 |
| 저빈도 | 관람이 드물어 캘린더가 비어 보일 수 있음 → 빈 상태 카피로 보완 |
| 직접 입력 | 커뮤니티 불가 사유를 화면에서 명확히 안내(클라이언트 비활성화뿐 아니라 서버에서도 강제 — §8 "버그 발생 지점" 참고) |

**단, 기록 캘린더에서 실제로 났던 버그를 그대로 반복하면 안 된다**(커밋 `2140dd4`). 아래 3개 가드를 반드시 함께 구현한다:

| 가드 | 내용 | 없으면 생기는 일 |
|---|---|---|
| **카운트 준비 여부** | 이동 판정은 "이번 달 카운트를 실제로 fetch 완료했을 때"만 한다. 캐시에 값이 있다는 이유로 ready를 true로 올리지 않는다(§8 "최적화"의 캐시 원칙과 동일) | 스테일 카운트로 "빈 날"을 오판해 이미 티켓이 있는 날에도 등록 화면으로 튐 |
| **재진입 시 무효화** | 티켓 생성 후 돌아왔을 때 dirty flag로 캐시를 비우고, 카운트 ready를 **다시 false로 내린 뒤** 재조회한다 | 방금 만든 티켓이 카운트에 반영되지 않아 같은 날을 또 탭하면 등록 화면으로 다시 이동, 중복 생성 |
| **더블탭 방지** | `navigatingRef`로 라우팅 진행 중 재진입을 막고, 실패 시에만 해제한다 | 연타로 등록 화면이 2번 push되거나 티켓이 2건 생성 |

카운트 로딩이 아직 끝나지 않았으면(월 전환 직후 등) 이동하지 않고 **선택 토글로 폴백**한다. 이 폴백 상태에서 목록이 비면 하단 목록 섹션 자체를 렌더링하지 않는다(`{selectedDateTickets.length > 0 && (...)}` — 별도 빈 문구 없음).

**포스터 비율 — 0.7로 통일**

### 저장 중 상태 · 로딩 · 에러 · 비로그인 (전 화면 공통)

앞의 화면별 레이아웃이 "정상 상태"만 그리고 있어, 여기에 나머지 3개 상태를 공통 규칙으로 못 박는다. 기존 화면(`app/performance/[id]/reviews/new/page.tsx:241-274`, `app/record/new/page.tsx:966`)과 **완전히 동일한 패턴**을 쓰고 새로 만들지 않는다.

**1) 저장 중 — `LoadingOverlay`**

생성·수정·삭제 버튼을 누른 순간부터 응답까지 `{saving ? <LoadingOverlay /> : null}`을 `<MobileContainer>` 바로 아래에 둔다. 동시에 해당 버튼은 `disabled={saving}`으로 막는다. 오버레이만 있고 `disabled`가 없으면 안 되고, 반대도 안 된다 — 오버레이는 시각 차단, `disabled`는 실제 중복 제출 차단이라 역할이 다르다.

| 화면 | `saving` 트리거 |
|---|---|
| S4 티켓 등록 | 저장 버튼 → `POST /api/tickets` + 이미지 업로드·링크 완료까지 |
| S5 티켓 수정 | 저장 버튼 → `PATCH /api/tickets/[id]` + 이미지 처리 완료까지 |
| S5 티켓 삭제 | `AlertDialog` 확인 → `DELETE` 응답까지 |
| S6 리뷰 작성 | 등록 버튼 → `POST /api/tickets/[id]/review` 응답까지 |

특히 S6는 서버 멱등 가드(409)와 **둘 다** 필요하다. 서버 가드는 최후 방어선이고, 버튼 disable은 유저가 중복 시도 자체를 못 하게 하는 1차 방어선이다.

**2) 로딩 중 — `Spinner`**

데이터를 불러오는 동안:
- **티켓북 홈(S2)**: 캘린더 골격(요일 헤더 + 셀 그리드)은 즉시 그리고 포스터 자리만 비워 둔다 — 기록 캘린더와 동일하게 레이아웃 점프를 만들지 않는다.
- **티켓 상세(S5) · 수정 · 리뷰 작성(S6)**: 화면 전체 중앙 `<Spinner size="lg" />` (`min-h-screen items-center justify-center`).

**3) 비로그인**

티켓북은 전부 본인 데이터라 로그인이 전제다. 기존 리뷰 작성 화면과 **한 글자도 다르지 않은 구조**를 쓴다.

```
useEffect: loading 끝났는데 !user → openLoginSheet()
if (loading) → 중앙 Spinner
if (!user)   → 중앙 정렬 안내 + [로그인하기] 버튼(h-11, max-w-[240px], bg-[#17171c] text-white)
```

화면별 안내 카피(톤은 기존 "로그인하면 리뷰를 작성할 수 있어요."와 동일):

| 화면 | 카피 |
|---|---|
| 티켓북 홈(S2) | 로그인하면 관람한 공연을 티켓북에 모을 수 있어요. |
| 티켓 등록(S3·S4) | 로그인하면 티켓을 등록할 수 있어요. |
| 티켓 상세·수정(S5) | 로그인하면 티켓을 볼 수 있어요. |
| 리뷰 작성(S6) | 로그인하면 리뷰를 작성할 수 있어요. |

**4) 진입점(공연 탭 헤더)의 비로그인 처리**

티켓북 아이콘 자체는 **숨기지 않는다**(기능 발견성 우선). 탭하면 티켓북 홈으로 이동하고, 홈에서 위 3)의 비로그인 화면을 만난다 — 헤더에서 조건부로 감췄다 나타났다 하면 로딩 중 아이콘 깜빡임이 생기고, 이미 §8.6에서 지적한 스켈레톤/실제 헤더 이중 마크업 문제와 겹쳐 버그가 되기 쉽다.

**5) 조회 실패 — toast + 정적 안내 텍스트 (재시도 버튼 없음)**

이 앱 전역에 "다시 시도" 버튼 UI가 없다(`app/performance/[id]/page.tsx:1061-1064`, `app/performance/search-input/page.tsx:532-535` 등 전부 toast + 정적 텍스트 조합). 티켓북도 동일 관례를 따르고 새 패턴을 만들지 않는다. 유저는 뒤로가기 후 재진입으로 재시도한다(자동 재시도 없음).

| 화면 | toast | 화면 텍스트 |
|---|---|---|
| 티켓북 홈(S2) 월 조회 | "티켓 정보를 불러오지 못했어요. 잠시 후 다시 시도해 주세요." | 없음(빈 그리드 유지) |
| 티켓 상세(S5) 단건 조회 | "티켓 정보를 불러오지 못했어요." | 중앙 "티켓 정보를 찾을 수 없어요." |
| 티켓 등록(S3) 검색 실패 | "공연 목록을 불러오지 못했어요. 잠시 후 다시 시도해 주세요."(기존 문구 재사용) | 없음 |
| 리뷰 작성(S6) 진입 조회 | "리뷰 작성 정보를 불러오지 못했어요. 잠시 후 다시 시도해 주세요." | 중앙 "정보를 찾을 수 없어요." |

검색 결과 0건은 기존 "조회된 공연이 없어요."(`search-input/page.tsx:534`)를 그대로 재사용한다.

| 항목 | 내용 |
|---|---|
| 별점 스케일 불일치(중요) | `performance_reviews.rating`은 기존 UI상 1~10 내부 스케일(별 1개 탭 = 2점)로 저장·평균된다. `performance_tickets.rating`은 PRD상 `smallint 1~5`다. 리뷰 작성 화면에서 "티켓 별점 자동 반영" 구현 시 `ticket.rating × 2`로 변환하지 않으면 기존 리뷰들과 평균 계산·별점 표시가 어긋난다. pe에게 명시적으로 전달 필요. |

## 8. 구현 계획 (pe)

> 작성: PE. 실제 코드(`app/`, `lib/`)와 Supabase(MCP: `list_tables`, `execute_sql`로 RLS·인덱스·FK 직접 조회)를 근거로 작성했다. 정리 순서는 "2. 기능 리스트"의 대분류 순서(티켓북 홈 → 티켓 등록 → 이미지 → 티켓 관리 → 커뮤니티 연계 → 진입점)를 따른다. 화면 레이아웃은 §7(PD)을 따르고, 여기서는 파일·CRUD·재사용 코드·버그 지점만 다룬다. **코드는 아직 작성하지 않았다.**
>
> 선행 확인 사항(전제): `performance_reviews.performance_id`는 `kopis_performances.mt20id`를 참조하는 **NOT NULL FK**다(MCP로 확인). 즉 직접 입력 공연은 구조적으로 리뷰를 가질 수 없다 — PRD의 "직접 입력 공연은 커뮤니티 노출 불가" 제약이 DB 레벨에서 이미 보장되므로, 앱·서버는 이 위에 이중 방어만 추가하면 된다.

- `calendar/page.tsx:716-760`의 무드/점선(planned) 표시 로직을 끌어오지 않을 것 — 티켓북은 단일 상태(관람 완료)뿐이다(PD §7 "기록 캘린더와의 시각 구분 규칙" 표와 일치, 훼손 금지).

- **날짜 탭 하단 목록은 별도 쿼리로 분리**: "최적화" 절의 월 조회 select(`id, watched_on, custom_title, performance_id`)는 캘린더 셀 렌더용 최소 컬럼이다. 하단 목록엔 `rating`·`custom_venue`가 더 필요한데, 매달 최대 31건 전체에 이 컬럼을 싣는 대신 **날짜 탭 시점에 `eq("watched_on", date)` 단건 조회를 한 번 더** 한다(`app/(tabs)/calendar/page.tsx:290-304`의 `fetchRecordsForDate`와 동일 구조 — 월 그리드와 날짜 상세를 분리하는 검증된 패턴). "같은 배열을 그대로 쓴다"는 접근은 컬럼이 부족해 실행 불가능하다.
- **하루 2건 이상일 때 "첫 포스터" 정렬 기준 확정 = `created_at ASC`**: 기록 캘린더는 셀에 무드 *평균*을 표시하므로 "첫 항목"이라는 개념이 없어 재사용할 선례가 없다(`moodAverages`는 그룹 평균이지 특정 1건 선택이 아님). 티켓북은 대표 포스터 1건을 뽑아야 하므로 같은 날짜 내 정렬을 `created_at ASC`(등록 순서, 안정적)로 고정한다. 정렬 기준을 정하지 않으면 재조회마다 대표 포스터가 바뀐다. **날짜 탭 하단 목록도 동일한 `created_at ASC`** 를 써서 "셀의 첫 포스터 = 하단 목록 첫 번째 항목"이 항상 일치하게 한다.
- 하루 2건 이상 배지(PD §7 "포스터 셀") 카운트는 `doneCounts`류의 별도 상태가 아니라 조회된 `performance_tickets` 배열을 `watched_on`으로 `groupBy`한 결과를 그대로 씀 — records 캘린더처럼 done/planned 두 갈래로 나누는 로직을 복사하지 않도록 주의.

앱 전체에 2단계 폼 전달 선례가 없다(확인: 기존 `sessionStorage` 용례는 `record-changed:*` 같은 dirty flag뿐이고 복합 데이터 전달 사례 0건, `record/new/page.tsx`는 단일 페이지 폼이라 애초에 전달이 불필요). 세션 상태를 쓰지 않고 **쿼리 파라미터만** 쓴다.

### 8.4 티켓 관리 (상세·수정·삭제)

**1) 수정·추가할 파일**
- 신규 `app/ticket/[id]/page.tsx`(S5, 상세)
- 신규 `app/ticket/[id]/edit/page.tsx`(수정)
- 신규 `app/api/tickets/[id]/route.ts` — `GET`(선택, 서버 조회가 필요하면)/`PATCH`
- 신규 `app/api/tickets/[id]/delete/route.ts` — `DELETE`

**2) CRUD 처리 방식**
- **R**: 상세 화면은 RLS로 본인 것만 조회 가능하므로 클라이언트 직접 조회도 가능하나, 이미지·공연 정보 조인이 필요해 서버 API(`GET`)로 한 번에 묶는 걸 권장.
  - **⚠️ `deleted_at IS NULL` 필터 필수**: `performance_tickets_select` RLS는 `user_id = (SELECT auth.uid())`만 검사하고 `deleted_at`은 **보지 않는다**(SQL 확인). 서버 API로 만들면 service role이라 RLS 자체가 무의미하므로 더더욱 앱 코드가 직접 걸어야 한다. 빠뜨리면 삭제한 티켓의 상세가 뒤로가기·북마크·캐시된 링크 재진입만으로 그대로 열린다. 없으면 404.
- **U**: `PATCH /api/tickets/[id]` — 대상 행 먼저 조회 → 없으면 404, `user_id !== auth.user.id`면 403(`app/api/reviews/[id]/route.ts:15-35` 패턴 그대로). 이미지 추가/삭제는 8.3의 별도 엔드포인트 재사용(단 `edit/page.tsx`의 두 실버그는 복제 금지 — §8.3 표 참고).
  - **바디 계약 = 전체 교체**: 매 요청에 `watched_on, rating, seat, memo` 4개 필드를 **항상 전부** 포함한다(부분 업데이트 아님). "필드 누락"과 "명시적 null"을 구분하지 않아도 되도록 계약을 고정해, `PATCH /api/reviews/[id]`가 겪는 부분 업데이트 함정(§8.5)을 애초에 만들지 않는다.
  - `seat`/`memo`: `app/api/reviews/[id]/route.ts:36-39`의 `trim() ? trim() : null` 패턴 그대로 — 빈 문자열을 null로 정규화.
  - `rating`: **리뷰 PATCH의 검증 로직을 그대로 복사하면 안 된다.** 리뷰는 `rating`이 NOT NULL이라 `2~10 짝수`를 무조건 요구하지만, 티켓의 `rating`은 nullable이다. `rating === null이면 통과 / 값이 있으면 0~10 짝수 검증`으로 분기한다. 별점 해제 UI(§8.2)가 `rating: null`을 보낼 수 있어야 하고 서버는 이를 정상 케이스로 받아야 한다.
- **D**: `DELETE /api/tickets/[id]/delete` — 소유권 확인 후 `deleted_at`만 갱신(하드 삭제 아님). **§6 확정 사항대로 연결된 `review_id`는 건드리지 않는다** — 리뷰 행 자체는 손대지 않고 유지.
  - `performance_ticket_images`도 **건드리지 않는다**. 근거: `records` 소프트 삭제(`app/api/records/[id]/delete/route.ts` 전문 확인)도 `record_media`를 전혀 손대지 않는 동일 관례이며, 이후 어떤 화면도 `record_media`를 부모 상태 확인 없이 단독 조회하지 않기 때문에(예: `app/profile/records/page.tsx:165-172`는 항상 `deleted_at IS NULL`로 거른 `records` id 목록으로만 조회) 안전하다. 티켓북도 `performance_ticket_images`를 **항상 티켓 id 목록으로만** 조회하는 한 동일하게 안전하다 — 이미지를 단독 조회하는 화면을 v1에서 만들지 않는다.
  - **이미 삭제된 티켓 재요청**: PATCH·DELETE 모두 대상 조회 시 `!row || row.deleted_at`이면 **404**(200 아님). 리뷰 삭제 라우트 패턴을 그대로 복제하면 자동으로 만족된다(확인 완료).
  - **동시성**: 낙관적 잠금 없이 마지막 쓰기가 이긴다. `records`·`performance_reviews` PATCH도 동일하게 동작하는 기존 관례이며 티켓만 강화할 근거가 없어 v1 범위에서 제외한다(확인 완료, 문제없음).

**3) 재사용할 기존 코드**

**4) 주의·버그 지점**
- 삭제 시 `review_id`를 null로 지우거나 리뷰까지 같이 지우는 실수를 하지 않도록 PATCH/DELETE 핸들러에 명시 주석 필요(§6에서 명확히 확정된 사항이라 재작업 시 혼동 여지 있음).
- 수정 화면에서 `performance_id`(원본 공연 참조)는 수정 불가 항목 — PRD 어디에도 "공연 재선택"은 없음. 수정 폼에 실수로 공연 선택 UI를 다시 노출하지 않도록 주의.
- **S5 "리뷰 쓰기" 버튼의 3번째 상태**: `ticket.review_id`가 있으면 라벨을 "작성한 리뷰 보기"로 바꾸고 `/performance/{ticket.performance_id}/reviews/{ticket.review_id}`로 이동시킨다(§7 참고). 이 분기가 없으면 유저가 폼을 전부 채우고 등록을 눌러야 비로소 409로 튕긴다. 아래 "리뷰 삭제 시 역방향 정합성"이 함께 반영되어야 이 버튼이 **죽은 리뷰로 이동**하는 사고가 안 난다.

**🔴 리뷰 삭제 시 티켓 `review_id` 역방향 정합성 (신규 발견, 치명)**

**재현**: 유저가 티켓에서 리뷰를 씀(`ticket.review_id = R1`) → 공연 상세 쪽 기존 화면에서 그 리뷰를 삭제 → 티켓은 여전히 `review_id = R1`을 들고 있음 → `POST /api/tickets/[id]/review`의 409 가드(`review_id IS NOT NULL`)에 걸려 **그 티켓은 영원히 새 리뷰를 못 쓴다**. 죽은 리뷰를 가리킨 채 락업된다.

**왜 FK로 안 막히나**: `performance_tickets.review_id`의 `ON DELETE SET NULL`은 **하드 삭제에만 반응**하는데, 리뷰 삭제는 전부 소프트 삭제다(`app/api/reviews/[id]/delete/route.ts:37-40`, `app/api/admin/reviews/[id]/delete/route.ts:32-35` 둘 다 `UPDATE ... SET deleted_at`). FK가 발동할 일이 없다.

**조치**: 아래 두 파일을 **§8.5의 "수정·추가할 파일" 목록에 추가**하고, 리뷰 soft-delete와 같은 트랜잭션에서 `UPDATE performance_tickets SET review_id = NULL WHERE review_id = :id`를 실행한다. PM 확정에 따라 RPC로 원자화한다(§8.5 참고).
- `app/api/reviews/[id]/delete/route.ts` (유저 삭제)
- `app/api/admin/reviews/[id]/delete/route.ts` (어드민 삭제)

**`updated_at` 갱신 방식(확정) — DB 트리거**

MCP 확인 결과 `performance_reviews`엔 `updated_at` 컬럼은 있지만 갱신 트리거가 없고 `PATCH /api/reviews/[id]`도 직접 넣지 않는다 — **기존 리뷰 테이블은 `updated_at`이 사실상 방치돼 있다**(본 PRD 범위 밖의 기존 결함). 반면 `records`엔 `records_set_updated_at` `BEFORE UPDATE` 트리거가 공용 `set_updated_at()` 함수를 호출하는 형태로 있고, `set_notices_updated_at`·`touch_user_consents_updated_at` 등 동일 패턴이 여러 테이블에 적용돼 있다. `performance_tickets`는 리뷰가 아니라 **이 다수결 관례(트리거)** 를 따른다 — DB 마이그레이션에 트리거를 추가하면 PATCH 핸들러가 `updated_at`을 직접 넣지 않아도 되고 방치 사고를 원천 차단한다.

**2) CRUD 처리 방식**
- **C: Postgres RPC로 원자화 (PM 확정)**

  앱 코드에서 "insert → update → 실패 시 delete 보상"으로 짜지 **않는다**. 보상 방식은 **보상 자체가 실패하면** 고아 리뷰가 영구히 남고, `ticket.review_id`는 여전히 null이라 유저가 재시도하면 두 번째 리뷰가 또 생성돼 고아가 2개가 되는 경로가 남기 때문이다.

  대신 단일 Postgres 함수로 묶는다 — 프로젝트에 이미 `create_record_recurrences`(SECURITY DEFINER, 다중 insert, 실패 시 `RAISE EXCEPTION`으로 전체 롤백)라는 동일 패턴 선례가 있어 새 관례를 만드는 것이 아니다.

  `create_ticket_review(p_ticket_id, p_user_id, p_rating, p_content, p_is_public)` — 한 트랜잭션 안에서:

  > **`auth.uid()`를 쓰지 않는다.** 이 프로젝트의 RPC는 라우트가 `getUserFromRequest`로 인증한 뒤 `auth.supabaseAdmin`(service role)으로 호출하는 관례라(`app/api/records/recurrences/route.ts:85`) 함수 안에서 `auth.uid()`는 **항상 NULL**이다. 선례인 `create_record_recurrences`도 `p_user_id`를 인자로 받고, 실행 권한이 `service_role`에만 부여돼 있다(ACL 확인) — 그래야 클라이언트가 `p_user_id`를 조작해 타인을 사칭할 수 없다. 신규 RPC 2개도 동일하게 `REVOKE ... FROM PUBLIC, anon, authenticated` + `GRANT ... TO service_role`을 반드시 함께 적용한다.

  1. 티켓 조회 + 소유권 확인(`user_id = p_user_id`, `deleted_at IS NULL`) → 없으면 `TKT404`
  2. `review_id IS NOT NULL`이면 `TKT409` (= HTTP 409, 멱등 가드)
  3. `performance_id IS NULL`이면 `TKT400` (= HTTP 400, 직접 입력 공연은 커뮤니티 노출 불가)
  4. `performance_reviews` insert — `rating`은 티켓 값 그대로 복사(변환 없음), `is_public`은 인자값(기본 `false`)
  5. `performance_tickets.review_id` update
  6. `review_id`와 `performance_id`를 반환

  라우트 핸들러(`app/api/tickets/[id]/review/route.ts`)는 `supabase.rpc("create_ticket_review", {...})` 호출과 **에러 코드 → HTTP 상태 매핑만** 한다(`TKT404`→404, `TKT409`→409, `TKT400`→400, 그 외→500). 클라이언트는 409를 받으면 에러 토스트 대신 기존 리뷰 화면으로 이동시킨다(§7 "작성한 리뷰 보기"와 동일 목적지).

  서버 가드와 별개로 버튼 `disabled` + `LoadingOverlay`도 함께 건다(§7 "저장 중 상태" 참고) — 서버 가드는 최후 방어선, 버튼 차단은 1차 방어선으로 **둘 다** 필요하다.

  성공 응답에 `performanceId`를 포함해 클라이언트가 `invalidatePerformanceHomeCache()` + `invalidateDetailCache(performanceId)`를 **공개 여부와 무관하게 항상** 호출한다(`reviews/new/page.tsx:234-235`와 동일) — 안 하면 방금 공개한 리뷰가 공연 상세에서 캐시 때문에 안 보인다.

- **D(리뷰 삭제) 도 같은 방식으로 원자화**: 리뷰 soft-delete와 `performance_tickets.review_id = NULL` 복원을 한 트랜잭션으로 묶는다(§8.4 "역방향 정합성"). 유저 삭제·어드민 삭제 두 경로 모두 적용한다.
- **U(v1 제외) — 공개 재전환**: 리뷰 공개/비공개는 **작성 시점에만 설정**하고 이후 전환은 v1 범위에서 제외한다(PM 확정).
  - 이유 ①: 기존 `PATCH /api/reviews/[id]`(38-58행)는 바디에서 `rating`을 **항상** 읽어 `2~10 짝수`를 재검증하므로, `{ is_public: false }`만 보내면 `rating`이 0으로 떨어져 **400**이 난다. 지원하려면 부분 업데이트를 허용하도록 핸들러를 고쳐야 하고, 이는 **기존 리뷰 수정 플로우의 검증을 느슨하게 만드는 회귀 위험**을 동반한다.
  - 이유 ②: 재전환이 없으면 "비공개로 저장된 리뷰"는 v1 내내 이미지가 없고(리뷰 이미지 연결은 v2+), 공개였던 리뷰가 비공개로 바뀌는 경우도 없다 → `performance_review_images_select` 정책이 `USING (true)`인 기존 구멍이 v1에서는 노출되지 않는다.
  - **v2에서 재전환을 넣을 때의 선행 조건**(지금 고치지 않고 기록만 남긴다): (a) `PATCH /api/reviews/[id]`를 부분 업데이트 지원으로 변경, (b) `performance_review_images_select`를 댓글·좋아요와 동일하게 부모 리뷰 공개 여부 기준으로 강화 — 안 하면 비공개 전환된 리뷰의 사진이 계속 조회된다.
- **커뮤니티 기존 플로우(`/performance/[id]/reviews/new`) 회귀 방지**: 이 경로는 `is_public`을 body에 **아예 넣지 않는다** → DB `DEFAULT true`가 적용되어 기존처럼 항상 공개로 저장됨. 코드 변경 불필요, 단 티켓 리뷰 폼과 컴포넌트를 공유할 경우 `is_public` state가 실수로 섞여 들어가지 않도록 명확히 분리(PD §7 "디자인 관점 주의사항"의 `is_public` 기본값 함정과 동일 맥락).

**3) 재사용할 기존 코드**
- `app/performance/[id]/reviews/new/page.tsx`(별점 탭·`Textarea` 300자 카운터 — 이미지 업로드 섹션은 제외, PRD §5에서 리뷰 이미지 연결은 v2+ 제외).
- `app/profile/general/page.tsx`의 `Switch` 행 패턴(PD §7 지정).
- `app/performance/[id]/page.tsx`의 기존 리뷰 목록 렌더링(카드·별점·좋아요/댓글 카운트)을 그대로 쓰고 조회 쿼리에 `is_public` 필터만 추가.

**4) 주의·버그 지점**
- `performance_reviews.rating`은 `NOT NULL`인데 `performance_tickets.rating`은 nullable — 티켓에 별점이 없으면 리뷰 작성 화면에서 반드시 사용자가 별점을 새로 선택해야 저장 가능(기존 리뷰 작성 폼의 "별점을 선택해 주세요" 토스트, `reviews/new/page.tsx:100-103` 그대로 유지).
- 직접 입력 공연 리뷰 차단은 클라이언트 비활성화뿐 아니라 **서버에서도 강제**(위 2)-2 참고) — 그렇지 않으면 URL 직접 접근으로 우회 가능.
- 리뷰-티켓 연결을 RPC로 원자화하지 않고 앱 2단계 호출로 되돌리면 고아 리뷰(ticket에 연결 안 된 채 남는 review row)가 발생할 수 있다 — 위 C 항목 참고.
- 리뷰 삭제 시 `review_id` 복원을 빠뜨리면 그 티켓이 409 가드에 걸려 **영구 락업**된다(§8.4 "역방향 정합성"). 이 항목과 "S5 버튼 3번째 상태"는 서로 의존하므로 **반드시 함께** 구현한다 — 버튼만 먼저 넣으면 죽은 리뷰로 이동하는 사고가 난다.

```sql
            (count(*))::integer AS review_count

-- idx_performance_ticket_images_deleted_at 는 만들지 않는다 — 티켓당 최대 3장이고 항상
-- ticket_id(위 인덱스가 커버) 또는 소유자 스코프로만 조회한다. 단독 deleted_at 인덱스는
-- 이 규모에서 쓰기 비용만 늘린다.

ALTER TABLE performance_ticket_images ENABLE ROW LEVEL SECURITY;
-- ⚠️ 치명적 주의: 이 SELECT 정책을 `USING (true)`로 두면 안 된다.
-- performance_review_images_select가 `true`인 것은 리뷰가 원래 전부 공개였기 때문이고,
-- 티켓 사진은 본인만 보는 개인 아카이브다. `record-media` 버킷이 public이라 URL만 알면
-- 누구나 이미지를 열 수 있으므로, 정책이 `true`면 로그인한 아무나
-- `from("performance_ticket_images").select("url")`로 **전체 유저의 티켓 사진을 열람**할 수 있다
-- (티켓 행 자체는 막혀 있는데 이미지만 새는 구조). 따라서 record_media_select_own과 동일하게
-- 소유자로 제한한다.
CREATE POLICY performance_ticket_images_select ON performance_ticket_images FOR SELECT USING (user_id = (SELECT auth.uid()));
CREATE POLICY performance_ticket_images_insert ON performance_ticket_images FOR INSERT WITH CHECK (user_id = (SELECT auth.uid()));
CREATE POLICY performance_ticket_images_delete ON performance_ticket_images FOR DELETE USING (user_id = (SELECT auth.uid()));

-- 6) 리뷰 생성 원자화 RPC (PM 확정 — 앱 2단계 호출 + 보상 로직 대신)
--
--    호출 관례는 create_record_recurrences와 동일하다(MCP 확인):
--      · 라우트가 getUserFromRequest로 인증한 뒤 auth.supabaseAdmin(service role)으로 .rpc() 호출
--      · 따라서 함수 안에서 auth.uid()는 항상 NULL이다 — 절대 쓰지 말고 p_user_id를 인자로 받는다
--      · p_user_id를 클라이언트가 직접 넘길 수 있으면 타인 사칭이 되므로, 실행 권한을
--        service_role에만 준다(create_record_recurrences의 ACL이 정확히 이 형태다)
CREATE OR REPLACE FUNCTION create_ticket_review(
  p_ticket_id uuid,
  p_user_id   uuid,
  p_rating    smallint,
  p_content   text,
  p_is_public boolean
) RETURNS TABLE (review_id uuid, performance_id text)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_ticket performance_tickets%ROWTYPE;
  v_review uuid;
BEGIN
  -- 소유권 + 미삭제 확인. 없음/타인 소유/삭제됨을 모두 404로 합쳐 존재 여부를 노출하지 않는다.
  SELECT * INTO v_ticket FROM performance_tickets
    WHERE id = p_ticket_id AND user_id = p_user_id AND deleted_at IS NULL;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'TKT404' USING ERRCODE = 'P0001';
  END IF;

  -- 멱등 가드: 더블탭·WKWebView 재시도로 리뷰가 2건 생기는 것을 막는다.
  IF v_ticket.review_id IS NOT NULL THEN
    RAISE EXCEPTION 'TKT409' USING ERRCODE = 'P0001';
  END IF;

  -- 직접 입력 공연은 커뮤니티 노출 불가(클라이언트 비활성화는 우회 가능하므로 여기서 강제).
  IF v_ticket.performance_id IS NULL THEN
    RAISE EXCEPTION 'TKT400' USING ERRCODE = 'P0001';
  END IF;

  -- performance_reviews.rating / content 는 둘 다 NOT NULL이다(MCP 확인).
  IF p_rating IS NULL OR p_content IS NULL OR btrim(p_content) = '' THEN
    RAISE EXCEPTION 'TKT400' USING ERRCODE = 'P0001';
  END IF;

  INSERT INTO performance_reviews (performance_id, user_id, rating, content, is_public)
  VALUES (v_ticket.performance_id, p_user_id, p_rating, btrim(p_content), COALESCE(p_is_public, false))
  RETURNING id INTO v_review;

  UPDATE performance_tickets SET review_id = v_review WHERE id = p_ticket_id;

  RETURN QUERY SELECT v_review, v_ticket.performance_id;
END;
$$;

REVOKE ALL ON FUNCTION create_ticket_review(uuid, uuid, smallint, text, boolean) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION create_ticket_review(uuid, uuid, smallint, text, boolean) TO service_role;

-- 7) 리뷰 소프트 삭제 + 티켓 역참조 복원 원자화 RPC
--    review_id의 ON DELETE SET NULL은 하드 삭제에만 반응하는데 리뷰 삭제는 전부 소프트 삭제라
--    FK가 발동하지 않는다. 복원을 빠뜨리면 그 티켓이 TKT409 가드에 걸려 영구 락업된다.
--    p_user_id가 NULL이면 소유권 검사를 건너뛴다(어드민 삭제 경로) — 이 인자를 클라이언트가
--    조작할 수 없도록 위와 동일하게 service_role 전용으로 권한을 제한한다.
CREATE OR REPLACE FUNCTION soft_delete_review(
  p_review_id uuid,
  p_user_id   uuid DEFAULT NULL
) RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_owner uuid;
BEGIN
  SELECT user_id INTO v_owner FROM performance_reviews
    WHERE id = p_review_id AND deleted_at IS NULL;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'RVW404' USING ERRCODE = 'P0001';
  END IF;
  IF p_user_id IS NOT NULL AND v_owner IS DISTINCT FROM p_user_id THEN
    RAISE EXCEPTION 'RVW403' USING ERRCODE = 'P0001';
  END IF;

  UPDATE performance_reviews SET deleted_at = now() WHERE id = p_review_id;
  UPDATE performance_tickets SET review_id = NULL WHERE review_id = p_review_id;
END;
$$;

REVOKE ALL ON FUNCTION soft_delete_review(uuid, uuid) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION soft_delete_review(uuid, uuid) TO service_role;
```

**RPC 에러 코드 → HTTP 매핑** (`app/api/tickets/[id]/review/route.ts`, `app/api/reviews/[id]/delete/route.ts`, `app/api/admin/reviews/[id]/delete/route.ts`)

| 코드 | HTTP | 의미 |
|---|---|---|
| `TKT404` / `RVW404` | 404 | 대상 없음, 타인 소유, 또는 이미 삭제됨 |
| `RVW403` | 403 | 타인 리뷰 삭제 시도(어드민 경로 제외) |
| `TKT409` | 409 | 이미 리뷰가 연결된 티켓 — 클라이언트는 토스트 대신 기존 리뷰 화면으로 이동 |
| `TKT400` | 400 | 직접 입력 공연이거나 별점·본문 누락 |
| 그 외 | 500 | — |

인증(401)은 RPC가 아니라 라우트의 `getUserFromRequest`가 처리한다 — RPC는 `auth.uid()`를 쓰지 않고 `p_user_id`를 인자로 받으므로(서비스 롤 호출이라 `auth.uid()`가 NULL이다) 인증 책임이 라우트에 있다. Postgres 예외 메시지는 `error.message`에 그대로 담겨 오므로 문자열 매칭으로 분기한다. 매칭되지 않는 에러는 **반드시 500으로 떨어뜨리고 로그를 남긴다** — 알 수 없는 실패를 200으로 흘려보내면 all-or-nothing 원칙이 깨진다.

**`lib/database.types.ts` 갱신 범위**: `performance_reviews` 블록(Row/Insert/Update 3곳)에 `is_public: boolean` 추가. 신규 RPC 2개는 `Database["public"]["Functions"]`에 시그니처를 추가해야 `supabase.rpc()` 호출이 타입 체크를 통과한다. 신규 테이블 2개는 알파벳 순으로 `performance_reviews` 다음, `performance_views` 이전에 `performance_ticket_images` → `performance_tickets` 순서로 삽입(`_`가 문자보다 앞이라 `performance_ticket_images` < `performance_tickets`).

**`app/api/account/delete/route.ts:6-25`의 `USER_SOFT_DELETE_TARGETS` 배열**에 `{ table: "performance_tickets", userColumn: "user_id" }`, `{ table: "performance_ticket_images", userColumn: "user_id" }` 추가 — 누락 시 회원탈퇴 후에도 티켓이 남는다.

### 최적화

> 아래 수치는 전부 Supabase MCP 실측(`EXPLAIN (ANALYZE, BUFFERS)`) 또는 실제 코드 확인 결과다. 추정치가 아니다.

**캘린더 월 조회 — 확정: 왕복 1회(1차), 실패 시 폴백 2회**

1차 시도(단일 임베디드 쿼리):
```
supabase.from("performance_tickets")
  .select(`
    id, watched_on, custom_title, performance_id,
    kopis_performances(poster),
    performance_ticket_images(url, deleted_at)
  `)
  .eq("user_id", user.id)
  .is("deleted_at", null)
  .gte("watched_on", monthStart)
  .lte("watched_on", monthEnd)
  .order("created_at", { ascending: true })
```
- 근거: `performance_tickets.performance_id → kopis_performances(mt20id)`와 `performance_ticket_images.ticket_id → performance_tickets(id)` 둘 다 FK 경로가 유일해 임베드 모호성이 없다(동일 구조의 `performance_reviews_performance_id_fkey`가 이미 프로덕션에 존재). `kopis_performances_select` RLS는 `USING (true)`라 임베드 대상 조회를 막지 않는다. `@supabase/supabase-js ^2.94.0`은 중첩 임베드 지원 버전.
- **✅ 스모크 테스트 통과(2026-09-12) — 채택 확정.** PostgREST에 위 select를 그대로 보내 `200 []`을 받았고, 대조군으로 존재하지 않는 관계(`ballet_brands`)를 임베드하면 `PGRST200 / 400 Could not find a relationship`이 나오는 것을 확인했다. 즉 200은 관계가 실제로 해석됐다는 뜻이다. 아래 폴백은 유지하되 1차 안을 그대로 구현한다.
- **⚠️ 이 코드베이스에 임베디드 조인 선례가 0건이다.** `kopis_performances`를 참조하는 11개 파일이 전부 `.in("mt20id", ids)` 개별 조회 + 클라이언트 병합만 쓴다. 착수 시 **스모크 테스트 1회로 실제 응답 구조를 확인한 뒤 채택**하고, 실패·불안정하면 즉시 아래 폴백으로 전환할 수 있도록 조회 함수를 한 곳에 격리해 둔다.

폴백(기존 관례, 왕복 2회):
```
// 1) 티켓 조회
const tickets = await supabase.from("performance_tickets")
  .select("id,watched_on,custom_title,performance_id,created_at")
  .eq("user_id", user.id).is("deleted_at", null)
  .gte("watched_on", monthStart).lte("watched_on", monthEnd);

// 2) 포스터·이미지 병렬 조회(calendar/page.tsx:178-196의 Promise.all 패턴)
const [posters, images] = await Promise.all([
  supabase.from("kopis_performances").select("mt20id,poster").in("mt20id", perfIds),
  supabase.from("performance_ticket_images").select("ticket_id,url").in("ticket_id", customTicketIds).is("deleted_at", null),
]);
```

- **비교 기준**: 기존 기록 캘린더는 월 진입 시 왕복 **3~4회**(`fetchCounts` 병렬 2회 + `fetchSettings` 1회 + `fetchRecordsForDate` 1회, `calendar/page.tsx:178-329`). 티켓북은 설정 조회가 없고 별점이 이미 결과에 포함돼 **1~2회**로 구조적으로 더 적다.
- 날짜 탭 시 하단 목록용 단건 조회가 1회 추가된다(§8.1 확정) — 월 진입 시점 비용이 아니라 탭 시점 비용이다.
- **인덱스 실측**: `records`(762행)에서 동일 형태 쿼리를 `EXPLAIN (ANALYZE, BUFFERS)` 한 결과, 부분 인덱스(`records_user_date_start_dedup_idx`)를 옵티마이저가 선택해 43행 반환에 **0.143ms**(Bitmap Index Scan). `performance_tickets_user_month_idx (user_id, watched_on) WHERE deleted_at IS NULL`도 동일 원리이며 테이블이 0행에서 시작하므로 최소 동급 이상이다.

**신규 인덱스 확정 — 5개 중 2개만 만든다**

| 인덱스 | 판정 | 사유 |
|---|---|---|
| `performance_tickets_user_month_idx` | **유지(핵심)** | 위 실측으로 효과 확인 |
| `performance_ticket_images_ticket_id_idx` | **유지** | 상세 조회 join 대상이자 `ON DELETE CASCADE`의 자식 스캔 대상 |
| `performance_tickets_review_id_idx` | **v1 생성 안 함** | `review_id`로 티켓을 되찾는 쿼리가 앱·서버 어디에도 없다. 리뷰는 항상 소프트 삭제라 `ON DELETE SET NULL`도 실제로 발동하지 않는다 |
| `performance_tickets_deleted_at_idx` | **v1 생성 안 함** | `records_deleted_at_idx`의 근거는 `user_id` 없이 전체를 세는 어드민 통계(`app/api/admin/stats/route.ts:26`)인데 티켓북 v1엔 그런 화면이 없다. 모든 조회가 `user_id` 선행 필터를 가져 부분 인덱스가 이미 커버 |
| `idx_performance_ticket_images_deleted_at` | **v1 생성 안 함** | 티켓당 최대 3장, 항상 `ticket_id` 또는 소유자 스코프로만 조회 |

불필요한 인덱스는 쓰기 비용만 늘린다. 해당 조회 패턴(어드민 티켓 화면, 리뷰→티켓 역참조)이 실제로 생기면 그때 추가한다.

**`is_public` 필터 추가의 성능 영향 — 지금은 인덱스 불필요**

- `performance_reviews` 실제 행 수는 **20건(활성 2건)**(실측). 이 규모에서 Postgres는 Seq Scan을 택하며 그게 인덱스 스캔보다 빠르다.
- `is_public` 조건을 넣은 `performance_engagement_summaries` 재정의 버전을 `EXPLAIN ANALYZE`한 결과 **베이스라인과 동일한 Merge Left Join 3단 플랜, 0.375ms** — 공연 홈·검색이 쓰는 핵심 VIEW에 회귀 없음.
- 댓글·좋아요 RLS의 `EXISTS` 서브쿼리는 Nested Loop Semi Join으로 평면화돼 **0.096ms** — 무시 가능.
- **임계치**: 활성 리뷰가 약 5,000~10,000건을 넘거나 공연 1건당 리뷰가 수백 건 단위가 되면 `(performance_id, is_public) WHERE deleted_at IS NULL` 복합 인덱스를 검토한다. 그 전까지 추가하지 않는다.

**캐시 전략**

```ts
// lib/ticketBookCache.ts
type TicketMonthData = { ticketsByDate: Record<string, TicketSummary[]> }; // 단일 상태 — done/planned 분기 없음
const monthDataMap = new Map<string, TicketMonthData>();

```
- **무효화는 항상 맵 전체 clear**. `lib/calendarHomeCache.ts`가 과거 "전역 dirty boolean" 방식에서 이 방식으로 교정된 이력이 있다 — 그 방식은 무효화 후 첫 달을 재조회하는 순간 플래그가 리셋돼 **이미 캐시된 다른 달이 stale로 남았다**. 티켓북은 처음부터 map-clear로 시작한다.
- dirty flag: `ticket-changed:<ticketId>`(생성·수정·삭제 시 `sessionStorage`에 set) → `app/ticket-book/page.tsx`의 `pageshow`/`popstate` 리스너에서 소비(`calendar/page.tsx:310-329`와 동일 구조: 키 제거 → `invalidateTicketBookCache()` → force 재조회).
- **"로드 완료(ready)" 플래그는 캐시 존재만으로 optimistic하게 세우지 않는다 — 실제 fetch 완료 시점에만 true로 올린다.** §7 "빈 날짜 탭"의 이동 판정이 이 플래그에 의존하므로, 이 원칙을 어기면 커밋 `2140dd4`의 스테일 오판 버그가 그대로 재발한다. 재조회 시작 시 ready를 다시 false로 내리는 것까지 포함한다.
- 리뷰 작성(S6)은 ticketBookCache 무효화 **불필요**(포스터·날짜·개수가 안 바뀐다). 대신 리뷰 생성 성공 시 `invalidatePerformanceHomeCache()` + `invalidateDetailCache(performanceId)`를 **공개 여부와 무관하게 항상** 호출한다(`reviews/new/page.tsx:234-235`와 동일).
- 티켓 상세(`/ticket/[id]`)·수정(`/ticket/[id]/edit`)은 **캐시 없이 매번 조회**. `app/record/[id]/page.tsx`·`app/performance/[id]/reviews/[reviewId]/page.tsx` 둘 다 자체 read 캐시가 없는 것이 이 코드베이스 상세 화면의 일관된 관례다. 저빈도 화면에 캐시를 넣으면 무효화 버그 위험만 늘고 이득이 없다.

**이미지 로딩**
- 캘린더 셀: `<AnimatedImage src={poster} width={34} height={48} sizes="34px" className="rounded-md object-cover" loading="lazy" />`
- **`loading="eager"`를 복사하지 말 것.** 기존 캘린더의 무드 아이콘이 eager인 이유는 로컬 정적 파일이기 때문이고(`calendar/page.tsx:726`), 포스터는 월 최대 31장의 원격 이미지라 정반대다.

**KOPIS 검색(S3)**
- 기존 `app/performance/search-input/page.tsx`는 디바운스 없이 Enter·버튼 클릭으로만 검색한다(403-408행). 동일 패턴을 유지하고 별도 디바운스·세션 캐시를 만들지 않는다(1회성 플로우).

**번들·라우트**

### Phase 1 — DB 마이그레이션 (단일 배포)

§8 "DB 마이그레이션"의 1~7번을 **하나의 마이그레이션으로** 적용한다. 이 SQL은 §9 "마이그레이션 드라이런 검증"에서 로컬 임시 PostgreSQL로 실행·동작 확인을 마쳤다(오류 0건, RPC 12건 + 권한 7건 통과). 쪼개면 `is_public` 컬럼만 있고 RLS가 없는 중간 상태가 생겨 비공개 리뷰가 전부 노출된다.

1. `performance_reviews.is_public` 추가
2. `performance_reviews_select` / `performance_review_comments_select` / `performance_review_likes_select` RLS 교체

### Phase 5 — 티켓 관리 (S5)

| 파일 | 내용 |
|---|---|
| 신규 `app/ticket/[id]/page.tsx` | 상세 |
| 신규 `app/ticket/[id]/edit/page.tsx` | 수정(S4 재사용 + 프리필, 공연 요약은 읽기 전용) |
| 신규 `app/api/tickets/[id]/route.ts` | `GET` / `PATCH` |
| 신규 `app/api/tickets/[id]/delete/route.ts` | `DELETE`(소프트) |

**핵심 체크리스트**
- [ ] **R에 `.is("deleted_at", null)`** — 없으면 404
- [ ] PATCH 바디는 4개 필드 **전체 교체**, `seat`/`memo`는 `trim() ? trim() : null`
- [ ] PATCH `rating` 검증은 **`null이면 통과 / 값 있으면 0~10 짝수`** — 리뷰 검증 복사 금지
- [ ] 삭제는 `deleted_at`만, `review_id`와 `performance_ticket_images`는 **건드리지 않음**
- [ ] 이미 삭제된 티켓에 대한 PATCH·DELETE는 **404**
- [ ] 수정 화면의 3장 카운트는 `visibleExistingCount` 기준
- [ ] 빈 필드(별점·좌석·메모 없음)는 **행 자체를 숨김**
- [ ] 포스터 비율 0.7로 통일, 미디어 캐러셀·닷은 재사용 안 함
- [ ] 삭제·저장 중 `LoadingOverlay` + 버튼 `disabled`

**완료 조건**: 생성 → 수정(별점 해제 포함) → 삭제 → 삭제된 URL 재진입 404 까지 1회 통과.

### Phase 6 — 커뮤니티 연계 (S6)

| 파일 | 내용 |
|---|---|
| 신규 `app/ticket/[id]/review/page.tsx` | 리뷰 작성 + 공개 설정 |
| 신규 `app/api/tickets/[id]/review/route.ts` | `POST` → `create_ticket_review` RPC 호출 |
| 기존 `app/api/reviews/[id]/delete/route.ts` | `soft_delete_review` RPC로 교체 |
| 기존 `app/api/admin/reviews/[id]/delete/route.ts` | 동일 |

**핵심 체크리스트**
- [ ] 라우트는 RPC 호출 + 에러 코드 → HTTP 매핑만(`TKT404`→404, `TKT409`→409, `TKT400`→400, 그 외 **500 + 로그**)
- [ ] 클라이언트는 409를 받으면 토스트가 아니라 **기존 리뷰 화면으로 이동**
- [ ] S5 버튼 3번째 상태("작성한 리뷰 보기")를 **역방향 정합성과 함께** 구현 — 따로 넣으면 죽은 리뷰로 이동
- [ ] 공개 설정은 **작성 시점에만**(재전환 v1 제외), 기본 OFF
- [ ] 커뮤니티 기존 플로우는 `is_public`을 body에 **넣지 않음**(DB DEFAULT true) — 폼 컴포넌트 공유 시 state가 섞이지 않게 분리
- [ ] 성공 시 `invalidatePerformanceHomeCache()` + `invalidateDetailCache(performanceId)`를 **공개 여부 무관 항상** 호출
- [ ] 티켓에 별점이 없으면 리뷰 작성 화면에서 새로 선택하도록 강제(기존 토스트 유지)

**완료 조건**: 공개/비공개 각 1건 작성 → 공연 상세 노출 여부 확인 → **리뷰 삭제 후 같은 티켓에 다시 리뷰 작성 가능**한지 확인(락업 회귀 테스트).
