# 미착수 작업 조사 기록 (2026-09-20)

> 착수하지 않기로 한 작업들의 설계와 조사 결과를 남긴다. 재개할 때 같은 조사를 반복하지 않기 위한 문서이며, **결정된 스펙이 아니라 조사 시점의 사실과 제안**이다. 코드가 바뀌었을 수 있으니 재개 전에 인용된 파일을 다시 확인할 것.
>
> 작성: PM, PD, PE 공동 조사. 관련: `PRD/ballet-note.md`, `admin_spec.md`, `design.md`

## 1. P0 — 빈 캘린더 첫 기록 카드

### 배경

가입자 39명 중 **13명(33%)이 기록을 한 번도 남기지 않았다.** 1건까지 합치면 44%다. 5건이 임계점으로, 넘기면 평균 활동 기간이 2.9일에서 15.4일 → 56.3일 → 99.2일로 뛴다. 첫 기록까지 걸린 시간이 평균 하루 이내라, 망설이다 떠나는 게 아니라 **아예 시작을 안 한다.**

2026-09-20 기준 기록 0건인 13명 중 **최근 30일 안에 앱을 만진 사람이 2명** 있다.

### 설계 (PD 확정)

기록이 0건인 계정에만, 캘린더의 월간 요약 배너 자리에 카드를 띄운다.

```
┌─────────────────────────────────┐
│ 첫 기록을 남겨볼까요?           │
│ 오늘 연습한 수업을 남기면        │
│ 캘린더에 차곡차곡 쌓여요.        │
│                                 │
│ [      첫 기록 남기기      ]    │
└─────────────────────────────────┘
```

| 항목 | 값 |
|---|---|
| 노출 조건 | 계정 전체 기록 **0건**. `status` 필터 없음(전체 행 기준) |
| 노출 방식 | 0건인 동안 **상시**. 첫 기록 시 자동으로 사라짐. 닫기 버튼 없음 |
| 위치 | `monthSummary` 배너와 같은 슬롯(`mx-2 mt-3 mb-2 rounded-xl`) |
| 동작 | 시트 없이 바로 `/record/new` |
| 컴포넌트 | `<p>` → `<div className="p-4">` + `Button`. **신규 컴포넌트 불필요** |

**온보딩 화면은 만들지 않기로 했다.** 첫 기록까지 평균 하루 이내라 이해 부족이 아니라 동기 부족이고, 가입 직후 약관 동의 시트를 이미 거치는데 모달을 또 얹으면 오히려 이탈 요인이 된다.

**게이미피케이션도 기각했다.** 진행률 바("3/5")는 유도당한다는 인지를 주고, 스트릭은 발레가 주 1~2회라 쉽게 끊겨 죄책감을 만든다.

### 구현 시 반드시 처리할 것

| # | 항목 | 안 하면 |
|---|---|---|
| 1 | **계정 전체 0건 신호를 새로 만들어야 한다** | `monthSummary`는 **이번 달** 기준이라, 기록이 쌓인 계정도 이번 달만 비면 "첫 기록" 오탐. 달을 스와이프할 때마다 켜졌다 꺼졌다 한다 |
| 2 | tri-state(`null`/`true`/`false`)로 두고 **`=== false`일 때만** 렌더 | `!hasAnyRecord`로 쓰면 `null`이 falsy로 묶여 기록 있는 유저에게 카드가 깜빡인다 |
| 3 | `lib/calendarHomeCache.ts`에 별도 모듈 변수로 캐시 + `invalidateCalendarCache`에서 함께 리셋 | 첫 기록 후 돌아와도 카드가 안 사라진다. 삭제로 0건 복귀도 같은 시그널로 커버된다 |
| 4 | `pt-4` 조건을 `!monthSummary && !showCard`로 갱신 | 카드 위에 불필요한 여백이 겹친다 |
| 5 | 버튼에 `ensureConsent()` 유지 | 다른 `/record/new` 진입점과 동의 처리가 어긋난다 |

헤더 `+` 버튼은 이제 `AddRecordEntrySheet`(오늘/예정/반복 3옵션)를 거치지만, **카드는 의도적으로 바로 이동한다.** 한 번도 기록해본 적 없는 사람에게 예정과 반복은 의미가 없고, 선택지를 늘리면 단일 행동 유도라는 목적에 반한다.

### 미결정

카드 배경색을 기존 배너와 같은 `bg-brand/8`로 할지, 중립 `bg-[#17171c]/5`로 할지. PD는 같은 슬롯에서 배타적으로 나타나므로 연속성 측면에서 전자를 권하되, 카드에 버튼이 있어 존재감이 커지니 후자도 괜찮다고 봤다.

### 구현 지점

| 파일 | 변경 |
|---|---|
| `lib/calendarHomeCache.ts` | 변수 1개, 함수 2개 |
| `app/(tabs)/calendar/page.tsx` | state 1개, 조회 1개, 렌더 분기 1곳 (배너: 596~610행) |
| `docs/design.md` | 카드 스펙 |

## 2. 수업 3시간 전 푸시 알림

### 인프라 현황 (검증됨)

| 구성요소 | 상태 |
|---|---|
| `lib/expoPush.ts` — Expo Push API 호출 | ✅ 동작. 호출부는 리뷰 댓글·좋아요 3곳뿐 |
| `profiles.expo_push_token` | ✅ 토큰 6개 저장(전체 40명 중) |
| 크론 인프라(`cronAuth`, `cronRunLogger`, `cron_job_runs`) | ✅ 3종이 매일 정상 실행, 438건 기록 |
| **"오늘 예정" 크론 라우트** | ❌ **없음** |

`user_notifications`가 0건인 이유는 인프라 부재가 아니다. 현재 푸시 트리거가 리뷰 댓글·좋아요뿐인데 그 데이터가 0건이라 **보낼 일이 없었다.**

### 핵심 설계 — 고정 창이 아니라 캐치업

**Vercel Cron 실행이 예정보다 평균 12~13분, 최대 57분 늦다**(30일 실측). 30분 간격과 겹치면 두 실행 사이가 최대 87분까지 벌어져 고정 폭 창은 구멍이 생긴다.

```sql
start_instant > now()                          -- 아직 시작 안 함
AND start_instant <= now() + interval '3 hours' -- 3시간 이내 임박
AND reminder_sent_at IS NULL                    -- 아직 안 보냄
```

크론이 늦어도 다음 실행에서 다시 걸리고, 수업이 이미 시작했으면 자동으로 빠져 뒤늦은 알림을 막는다. 실제 도달은 "정확히 3시간 전"이 아니라 "3시간 전 ~ 주기+지연만큼 늦게" 사이가 된다.

주기 제안: `*/30 * * * *`(하루 48회).

### 필요한 작업

| # | 항목 | 내용 |
|---|---|---|
| 1 | `records.reminder_sent_at timestamptz NULL` | 중복 발송 방지. 레코드 1건 = 대상 1건이라 별도 테이블 불필요 |
| 2 | `profiles.class_reminder_enabled boolean NOT NULL DEFAULT false` | `haptic_enabled`와 같은 패턴, **기본값만 반대**(옵트인) |
| 3 | `get_due_class_reminders()` RPC | 자정을 넘나드는 3시간 창을 SQL로. PostgREST로는 이 연산 필터를 표현 못 함 |
| 4 | `records` 부분 인덱스 | `WHERE status='planned' AND deleted_at IS NULL` |
| 5 | `/api/cron/class-reminder` | 기존 크론 패턴(`assertCronAuthorized` → `startCronRun` → 작업 → `finishCronRun`) |
| 6 | `vercel.json` 등록 | |
| 7 | 앱 설정 토글 | `app/profile/general/page.tsx`, 진동 옆 |
| 8 | RN 권한 요청 브릿지 | 왕복 메시지 |

### 주의할 점

**`sendExpoPushToUser`는 항상 `void`를 반환한다**(`lib/expoPush.ts:19-69`). 실패해도 `console.error`만 찍는다. 크론이 "보냈다"를 판정할 근거가 없으므로, 구현 시 `{ ok: boolean }`을 반환하도록 개선하고 실패 건수를 `cron_job_runs.counts_json`에 남기는 게 좋다. 기존 3개 호출부는 반환값을 안 쓰므로 하위 호환이 유지된다.

**`PATCH /api/records/[id]`에서 `start_time`이나 `record_date`가 바뀌면 `reminder_sent_at`을 `null`로 리셋해야 한다.** 안 하면 시간을 옮긴 수업에 리마인더가 영영 안 간다.

**발송은 레코드 1건씩 개별 업데이트한다.** 전체를 모아 마지막에 일괄 업데이트하면 중간 실패 시 이미 보낸 것까지 재발송된다.

`profiles` 행은 프로필 탭 최초 진입 때 생성된다. 그 탭을 한 번도 안 연 유저는 토큰 등록도 토글 저장도 안 된다(`.single()`이 에러).

### RN 브릿지 스펙 제안 (RN 개발자와 합의 필요)

단방향으로 요청만 던지면 사용자가 권한을 거부해도 토글이 켜진 채 남아 "확인된 값만 표시" 원칙에 어긋난다. 왕복이 필요하다.

```
요청: { type: "notification_permission_request", version: 1, request_id }
응답: { type: "notification_permission_result", version: 1, request_id,
        status: "granted" | "denied" | "undetermined" }
```

`granted`를 받은 뒤에만 `class_reminder_enabled = true`를 저장하고, 그 외에는 토글을 원위치하고 토스트를 띄운다. `health_sync_request`/`health_sync_result`가 같은 왕복 패턴의 선례다.

### 현재 도달 가능 범위

| 지표 | 값 |
|---|---:|
| 앞으로 예정된 수업 | 113건 |
| 예정이 있는 사용자 | 3명 |
| **예정 + 푸시 토큰 둘 다** | **1명** (운영자 계정) |

99건을 깔아둔 사용자는 토큰이 없어 알림을 못 받는다.

### 확인이 필요한 것

| 항목 | 누가 |
|---|---|
| Vercel 플랜의 크론 개수·주기 제약 (30분 간격 가능 여부) | 대시보드 |
| `EXPO_ACCESS_TOKEN`이 Production에 설정돼 있는지 | 대시보드 |
| RN 앱이 권한 허용 시 토큰을 재등록하는지 | RN 개발 |

`assertCronAuthorized`는 `Authorization: Bearer <CRON_SECRET>`만 검사하고 Vercel 고유 헤더를 보지 않는다. 플랜 제약으로 30분 간격이 막히면 외부 스케줄러(GitHub Actions 등)로 같은 엔드포인트를 호출해 우회할 수 있다.

### 목적 구분

| 목적 | 적절한 시점 |
|---|---|
| 수업 출석 리마인더 | 수업 **전** (3시간 전) |
| 기록 유도 | 수업 **후** |

기록의 27%가 일주일 넘게 밀려 입력되는 문제는 **수업 후 알림**으로 풀린다. 3시간 전 알림은 다른 문제(수업을 까먹는 것)를 푼다.

## 3. 로그 정리(purge) 정책

### ⚠️ 그냥 지우면 사용자 화면이 바뀐다

`brand_engagement_summaries`와 `performance_engagement_summaries` 뷰가 `brand_views`/`performance_views`를 **엔티티별로 전체 기간 `COUNT(*)`** 한다. 그리고 이 `view_count`가:

- 브랜드 탭 "지금 주목받는 브랜드"의 정렬 기준(`score = view_count + like_count × 10`)
- 공연 탭과 검색 화면의 정렬

에 **직접 쓰인다.** 즉 로그를 지우면 어드민 카드만이 아니라 **실제 사용자에게 보이는 순위가 바뀐다.**

전역 카운터 하나로는 해결되지 않는다. **엔티티별 롤업 테이블**(`brand_id`/`performance_id`별 "삭제 전 누적치")이 필요하고, 두 뷰를 "라이브 최근 행 COUNT + 롤업 합"으로 재정의해야 한다.

`cron_job_runs`와 `user_notifications`는 집계 뷰나 카드에 쓰이지 않아 롤업 없이 삭제해도 안전하다.

### 보관 기간 제안

| 테이블 | 현재 행 수 | 일 증가 | 보관 | 근거 |
|---|---:|---:|---|---|
| `performance_views` | 131 | ~1.3 | 90일 | 차트가 최대 30일, MAU가 30일 롤링이라 3배 여유 |
| `brand_views` | 406 | ~2.4 | 90일 | 동일 |
| `brand_link_clicks` | 298 | ~1.7 | 90일 | 동일 |
| `performance_booking_clicks` | 75 | ~0.4 | 90일 | 동일 |
| `cron_job_runs` | 438 | 3 → **51** | 60일 | 어드민 화면에 노출 안 됨. 순수 운영 로그 |
| `user_notifications` | 0 | — | 읽음 180일 | 사용자에게 보이는 이력이라 PM 확인 필요 |

### 착수 시점

행 수 임계치로는 정당화되지 않는다(조회·클릭이 하루 1~2.5건). **실질적 트리거는 푸시 크론이다.** 30분 간격 크론이 배포되면 `cron_job_runs`가 하루 3건에서 **51건**으로 늘어, 현재 전체 로그량(약 1,300행)이 25일이면 다시 쌓인다.

**푸시 크론 배포와 같은 시점 또는 직후**에 하는 게 맞다. 데이터가 적을수록 롤업 백필이 가볍다.

### 구현 방식

pg_cron은 설치돼 있지만 `cron.job`이 비어 있어 이 프로젝트에서 검증된 적이 없다. **기존 Vercel Cron 패턴을 쓴다.** 하루 1회면 충분하다(보관 기간이 일 단위라 지연에 민감하지 않음).

`purge_soft_deleted_accounts()`는 **비활성 스텁**이다. 본문이 `jsonb_build_object('ok', true, 'disabled', true)`를 반환할 뿐이고 호출부도 없다. 참고할 패턴이 아니다.

## 4. 발레노트 §8 결정

`PRD/ballet-note.md` §8의 미결정 4가지에 대한 PD 판단이다.

| # | 쟁점 | 결정 | 근거 |
|---|---|---|---|
| 1 | 프로필 카드 위치 | **"기록 요약" 바로 아래** | 둘 다 "이번 달/올해 스냅샷" 성격. 자주 만난 선생님·장소는 랭킹형 탐색이라 성격이 다름. 아래로 내릴수록 발견성 하락 |
| 2 | 집계 전환 UI | 헤더 1단 우측 **아이콘 버튼** | 화면 이동이지 표시 모드 토글이 아님. 토글로 만들면 "홈이 두 모드를 가진다"는 잘못된 신호. S4 내부의 월/년 전환은 토글이 맞음 |
| 3 | 어드민 화면 | **v1부터 포함** | 금액은 민감 데이터. CS 문의 시 조회 수단이 없으면 티켓북보다 곤란. 스코프가 조회만이라 비용도 낮음 |
| 4 | 금액 축약 | 캘린더 셀 배지에만 | 다른 화면은 공간이 넉넉하고 정확도가 중요 |

### 금액 축약 규칙

| 금액 | 표기 |
|---|---|
| 8,500 | `8,500` (1만 미만은 원 단위) |
| 85,000 | `8.5만` |
| 128,000 | `12.8만` |
| 1,000,000 | `100만` (딱 떨어지면 소수부 생략) |
| 1,250,000 | `125만` |
| 1억 이상 | `1.2억` |

소수 첫째 자리까지, **버림**. 반올림하면 실제보다 커 보여 신뢰를 해친다. 같은 날 여러 건이면 합계에 적용한다.

배지 색은 `--brand`와 `--alert`를 쓰지 않고 베이스 다크 투명도만 쓴다(`bg-[#17171c]/8`). 기록 캘린더와 혼동을 막으려면 감정 이미지를 빼는 것만으로는 부족하고 **색 체계도 달라야** 한다.

### 문서 모순

**§6 MVP 범위 표는 "어드민 목록과 상세"를 v1 포함으로 적었는데 §8은 같은 항목을 "미결정"으로 남겨뒀다.** §6이 맞다고 보고 §8에서 해당 항목을 지우면 된다.
